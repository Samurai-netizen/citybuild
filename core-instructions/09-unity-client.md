## AI-friendly Unity rules (Claude cannot use the Editor GUI)
1. **Minimal scenes.** `Bootstrap.unity` is empty: `GameBootstrap` creates the one `GameRoot` GameObject when a scene
   named `Bootstrap` loads (a `GameRoot` already in the scene is kept). Everything else is
   created from code at runtime. Avoid hand-editing scene or prefab YAML.
2. **UI Toolkit** (UXML + USS text files) for all screens and HUD — readable and diffable. The UXML, USS and
   `PanelSettings` that code loads by name live in `Assets/_Project/Resources/UI/` (decision 024).
3. **Art from the Era I models** (CR-0005): FBX files made by `art/blender/` that sit in `Assets/_Project/Art/Resources/Models/` (so a player build has them) and are loaded by name with `Resources.Load` (`Models/era<N>/<typeId>_l<level>`, decision W16), all drawn with one shared URP material. Primitives (`GameObject.CreatePrimitive`) are only the fallback for a level or a type with no model, the hover and selection markers and the tile hints. No prefabs are required for the MVP; if one is needed, create it with an editor script. The UI pictures are 256 px PNG icons in `Assets/_Project/Resources/UI/Icons/` (the only copy; `art/blender/render_ui.py` writes there), found by content id through `UiIcons` (`item_<id>`, `bld_<typeId>`, `res_<id>`, and `workers`, `builders`, `research`; CR-0005-T4); an editor script sets their import settings, and a test fails for an item, building type or research node of the content that has no icon. A view with no picture keeps its text.
4. When a step needs the Editor (creating the project, assigning a scene to Build Settings,
   pressing Play), write exact click-by-click **[MANUAL]** instructions instead of guessing.

## Runtime structure
- **Composition root:** `GameRoot` builds services by hand (no DI framework, no singletons, no static mutable state) and draws nothing itself: a screen is a component of its own (`ConnectionStatusView`, `BuildMenu`, `PlacementBar`, `ToastHost`).
  `GameBootstrap` (a `sceneLoaded` handler registered before the first scene) creates it when the `Bootstrap` scene loads.
- **Core:** `ClientCityStore` holds the last snapshot + receive time; raises `SnapshotChanged`.
  Ignores snapshots whose `stateVersion` is lower than the current one (out-of-order responses), and the same version with the same or an
  earlier clock (the same city, for example a late replay: taking it would move the display clock back). The snapshot's city never leaves it
  uncopied: readers get `CopyCity()`. `SnapshotMapper.Apply` (Net) is the way from an answer to the store; a refused command never changes it.
- **Display prediction:** `DisplayClock` = `snapshot.clock + whole secondsSinceReceived × rules.timeScale`
  (`timeScale` is 1 except on Development servers using `DevTimeScale`). For counters and
  progress bars, `DisplayCity` runs `Simulator.Advance` on a **copy** of the snapshot, at most once per second and always from the snapshot, so it
  equals one advance of the whole time (the production cap counts from the start of an advance). A new snapshot replaces it at once. Views use the `Simulation.Display` helpers (`04` §15) for rates,
  bars and countdowns. Never send predicted values anywhere. In the Editor and development builds, `PredictionWatch` (M0-54) logs a warning at a new snapshot when the display's clock went back or the snapshot differs from the engine run on the one before it (no command on its way), with the cities as JSON (`docs/testing/LOCAL-E2E.md`).
- **Net:** `ApiClient` (`UnityWebRequest` wrapped in a `Task` that continues on the main thread; base URL and timeout from the
  `ApiClientSettings` asset), one method per endpoint of `05`, each returning an `ApiResult<T>`: the DTO or an
  `ApiError { Code, Status, Detail, TraceId, RequestId, RetryAfterSeconds }` parsed from Problem Details. A rule's refusal, a lost
  connection (`CLIENT_NETWORK_ERROR`), a timeout (`CLIENT_TIMEOUT`) and a body that is not the contract's, such as a proxy's 502 page
  (`CLIENT_INVALID_RESPONSE`), are results; only a cancelled token throws (cancel with `destroyCancellationToken`).
- **Start (M0-38):** `GameRoot.Start` runs `StartupFlow`: `AuthService` takes a kept token for the configured dev player or calls the dev
  login, `ContentService` turns `GET /content` into `GameContent` through `GameContentFactory` (so the client trusts no content its own
  engine would refuse), then `GET /city`, whose snapshot goes into the store (`GameRoot` then builds `DisplayCity` and refreshes it in `Update`). The token is in memory; the Editor and development players also keep it in `PlayerPrefs`
  (keys `CityBuilder.DevLogin.*`), never a snapshot or a balance. A kept token the server refuses (`AUTHENTICATION_REQUIRED`) is dropped
  and the flow logs in once more. Invalid content shows the fatal error screen (`UI/FatalError`); a failed request shows "Not connected"
  with a sentence and the code. The dev player's name is `devDisplayName` in `ApiClientSettings`.
- **Commands (M0-40):** `CommandSender` (Net) creates the `requestId` once per player intent (`CommandIntent`) and reuses it on every attempt.
  Retries only on network errors, timeouts, 5xx and `CONCURRENCY_CONFLICT`: at most 3 requests, waits 0.5 s then 1 s (`CommandPolicy.Default`
  holds 0.5/1/2; the 2 s would precede a 4th request). Any other 4xx (also `RATE_LIMITED`) is final. On success the snapshot goes to the store
  through `SnapshotMapper.Apply`. A command refused with `AUTHENTICATION_REQUIRED` makes `GameRoot` ask the monitor for a poll at once, whose new login serves the player's next try (M0-54). `Pending` lists the intents on their way (`Waiting`, `Sending`, `Retrying`) for ghosts and disabled buttons;
  a repeat of a pending intent shares its result. `AssignWorkers` targets are coalesced per building: a new target replaces a not-yet-sent one,
  is sent after a 400 ms pause with no newer one, and waits for the building's earlier target to end. `GameRoot` builds the sender once connected.
- **Polling (M0-41):** `GET /city` on start (the start flow's own), on `OnApplicationPause(false)`, after the device's network comes back, and every 120 s in the
  foreground; nothing while paused, one poll at a time (`PollScheduler`). `ConnectionMonitor` (Net) puts each snapshot in the store and holds the
  `ConnectionState` (`Connecting`, `Connected`, `Offline`, `Unauthorized`, `ServerError`, `IncompatibleVersion`): a refused token gets one new login and one
  repeat, then `Unauthorized`, and the answer to that repeat replaces the city whatever its version (it may be a new city, CR-0004); content of another version is `IncompatibleVersion` and is not applied. `GameRoot` ticks it in `Update` and shows the state. A command that ends with no answer or a 5xx (the sender gave up after its repeats) also asks for a poll, so the state turns `Offline` or `ServerError` at once (M0-55). `PollFinished` says when a poll ended.
- **City view (M0-43):** `GameRoot.Awake` creates `CityWorld` first: the one `City Camera` (tag `MainCamera`, solid dark background, perspective, yaw 45° and pitch 50°) and a sun, so the screen is cleared from the first frame. Once connected, `ShowGrid(new CityGrid(rules.GridWidth, rules.GridHeight))` builds the ground (an instance of the `tile_grass` model on every tile, CR-0005-T3) and the controls.
  Grid x is world x, grid y is world z, a tile is 1 unit, the ground is y = 0. A drag (one finger or the left mouse button) pans so the ground point under the pointer stays under it, clamped to the grid; a pinch or the mouse wheel zooms between 3 units and the distance where the whole grid fits; a tap selects the tile (again, or off the grid, clears it); the mouse pointer marks its tile. `TileSelection` is display state only: tile checks are UX hints, the server decides (`UX rules`).
- **Building views (M0-44, CR-0005-T3):** `CityView` (under `CityWorld`) reconciles one `BuildingView` per building of `DisplayCity.Current` by building id: a new id gets a view, a changed one is updated in place, a missing one is destroyed; `GameRoot` calls `CityWorld.ShowCity` on every `DisplayCity.Changed` (once a second), and a call where nothing changed allocates nothing. The look comes from `BuildingLooks` by `(typeId, city era, level)`: the model `Models/era<N>/<typeId>_l<level>` (a later era without art of its own keeps the latest earlier era's model); while the building is `Constructing` or `Upgrading` the `construction_site` model of the era instead, so nothing finished shows before the server says so (an upgrade shows the site, then the next level). A level with no model falls back to the type's primitive look of M0-44 (20 % taller per level; a low foundation while constructing, only if there is no site model), and a type nobody knows is a grey box, never an exception. A model is never stretched; models share the art's one material (no copy per building; the stalled look is a per-renderer property block, M0-50). The view finds `Anchor_Status`, `Anchor_Door`, `Anchor_Smoke`, `Anchor_Stockpile` and `Wheel` by name once when it builds the body (null when a model has none); only `Anchor_Status` is used so far (the status below) and nothing turns the wheel. A unit test fails when a building type of the content has no model for a level it can reach or a model lacks `Anchor_Status` / `Anchor_Door`. Views have no colliders and never call the server.
- **Building status (M0-50):** given the content, `CityView.Show` also draws each building's status. `BuildingStatusModel.Describe` works out a `BuildingStatus` from the displayed city with the engine's helpers: the ring is `Constructing`, `Upgrading` or `Producing` with `ProgressDisplay.ProgressPermille` at `city.Clock` (the `DisplayClock`'s second, since `DisplayCity` advanced the city to it); the bubble is `NoWorkers`, `MissingInput` or `StorageFull` with its item, from `StallReason` (a cottage's `NoRecipe` is no bubble, and a type the content does not know has none); the pips are the assigned workers, at most 6 (`BuildingStatus.MaxPips`, a layout limit, not a game number). `BuildingStatusView` (a child object `Status` of the building's view, made the first time there is something to show, so a cottage has none) draws it at the model's `Anchor_Status` and turns it to the camera: a ring of 32 steps (a shared mesh per step, so a new progress swaps a reference; a dark track, filled clockwise from the top: yellow while built, blue while upgraded, green while producing), a bubble (a rim of amber, red or blue, the picture of the workers or of the item from `UiIcons`, and a strike across the picture of a missing input) and a centred row of pips below. It draws only what differs from the last call, once a second with `DisplayCity.Changed`, and allocates nothing then (`StallReason` makes one small object per stalled building per second inside the engine). The pictures are made once by `StatusArt` and drawn with the pipeline's default sprite material (no shader is looked up by name). A stalled building (one with a bubble) also looks slightly washed out: `StalledTint` writes a property block on each renderer of its body (the base colour times 0.65 and a grey emission, a lerp toward grey), and removes it when the building runs again; the art's shared material is not copied, and has `_EMISSION` on with an invisible emission for this. The scaffold while constructing is the construction-site model (above). Display only: nothing here decides or sends anything.
- **Building inspector (M0-51):** a tap on a tile with a building opens the inspector (`BuildingInspector`, its own `UIDocument`, sort order 0.8; layout `UI/Inspector`) at the right under the HUD, while the placement flow is `Idle` (a card picked in the menu keeps the ground to the placement). `BuildingInspectorModel.Create` words the building from the content and the displayed city once a second: name, `Level 1 of 2`, the status (the engine's `StallReason` in words: `Waiting for Logs`, `Producing`, `No workers assigned`, …), the time to the next event (`ProgressDisplay.SecondsUntilNextEvent`), the recipe and the per-hour rates at the assigned workers (`ProductionDisplay.PerHour`, research included), the **worker stepper** and the upgrade section. The stepper shows `3 / 3`, − is off at 0, + is off at the level's maximum and when the free workers do not cover one more (the target already on its way counts against them), each with a note; the rates at the pending value show as `With 2 workers: …`. Upgrade shows the next level's cost, time and gain (`Max workers 3 → 6`) and, when it is off, the first reason in the server's order (busy, highest level, no free builder, `Not enough <items>`). **The pending state is the sender's:** `InspectorPending.From` reads the newest `AssignWorkers` target and any `UpgradeBuilding` of the building from `CommandSender.Pending`, so the stepper shows the target at once, the model switches a button off while its intent is on its way (a double tap cannot submit twice) and the value falls back to the server's by itself when the command ends. `InspectorFlow` sends `AssignWorkers(id, shown target ± 1)` (an absolute target; the sender coalesces rapid taps and sends after 400 ms) and `UpgradeBuilding(id)`; the answer is the snapshot in the store and a toast from `CommandFeedback`. Nothing is subtracted or changed before the server answers; every disabled state is a hint and the server checks again. A press over the panel is the UI's (`IsOverUi`). The inspector is a member of the menu group: opening the build menu's sheet closes it, and opening it (tapping a building) closes the sheet. Display only.
- **Research screen (M0-52):** a **Research** button at the bottom left, next to Build (`ResearchScreen`, its own `UIDocument`, sort order 0.9; layouts `UI/Research` and `UI/ResearchNode`), opens a panel over the city with the era header (`Early Middle Ages — 1 / 4 researched`, the nodes researched out of all nodes of the city's era), the rule `Complete all to advance` (greyed out while the content has no later era, as in M0) and the era's nodes as **one row of cards** (for the MVP; `ResearchScreen`, CR-0007): each card, from the top, has the name, the big picture (about 56 % of the card), the text lines (the effect, the status, the reason the node cannot be financed) and, as two chips over the picture, the time (top left) and the cost (bottom). **The whole card is the Finance button**: the `research-node-finance` Button is laid over it, invisible, so the card is the touch target; a card that can be financed has a green border and is off, with its reason in the note, when it cannot. The header's X is hidden; the Close button under the panel closes it. The model still gives each node a depth (`ResearchNodeModel.Column`: 0 for no prerequisite in the era, else one more than its deepest prerequisite), so the list has prerequisites first and a later tree of branches can use it (`ResearchScreenModel`, in the content's order inside a column). Each node (`ResearchNodeModel`) shows its picture (`UiIcons.ForResearch`), name, effect in words from the effect type and the content's names (`Unlocks Trading Post`, `Woodcutter's Hut: −20% labor`, `+250 Logs storage`), cost (`Cost: 300 Coins, 50 Logs`), duration (`Takes 45m`) and its status derived from the displayed city: **Locked** (`Requires: Sharpened Axes`, the missing prerequisites), **Available** (`Ready to research`), **In progress** (a ring from `ProgressDisplay.ResearchProgressPermille` and `In progress · 22m 30s left`) or **Done** (`Researched`). **Finance** is shown on a locked or available node and is off with one reason in the server's order (`CityRules.StartResearch`): `Another research is running`, then `Requires: …`, then `Not enough Coins`; it is a hint, the server checks again. Pressing it gives the sender `StartResearch(id)` (`ResearchFlow`); a start on its way (`ResearchPending`, read from `CommandSender.Pending`) shows `Starting research…` on that node and switches every button off, so a double tap cannot submit twice; nothing is subtracted before the server answers, and the result is a toast from `CommandFeedback`. The screen is a member of the menu group. Display only.
- **Welcome-back report (M0-53):** every snapshot the city store takes is looked at once (`WelcomeBackFlow`: the poll's, a command's and the first `GET /city`'s, which the startup stored before any view existed). When its `settlement` (`SettlementSummary` on the `CitySnapshot`, mapped by `SnapshotMapper`) covers **300 real seconds or more** (`WelcomeBackModel.ThresholdSeconds` × `rules.timeScale`, because a settlement counts city seconds, M0-54; a routine poll settles about 120 s, so it never qualifies), a modal panel (`WelcomeBackPanel`, its own `UIDocument`, sort order 2.5, layout `UI/WelcomeBack`: a full-screen scrim that takes the pointer and a card) shows `While you were away (7 h 12 m)` and, for what is not empty: **Produced** and **Used** with one line per item (`960 Logs`), **Buildings** (`Sawmill built`, `Woodcutter's Hut upgraded to level 2`, the same sentence counted: `Cottage built ×3`; a construction completes at level 1 and an upgrade at level 2 or more, which the snapshot's city shows) and **Research** (`Sharpened Axes — Woodcutter's Hut: −20% labor`, the effect words shared with the research screen: `ResearchEffectText`). When `productionSeconds < elapsedSeconds` a note adds `Production paused after 8 h. Check in more often or research storage.`; when nothing happened the card says `Nothing was produced or finished.`. **Continue** dismisses it (a tap on the scrim does not). The panel is a member of the menu group. Display only: it reads the server's report and decides nothing.
- **Build menu (M0-45):** `BuildMenu` (a `UIDocument` of its own, made by `GameRoot` once connected; layouts `UI/BuildMenu` and `UI/BuildCard`) shows one card per building type of the content, with the type's icon (`bld_<typeId>`, set once when the card is made). `BuildCardModel` holds a card's words: name, `Cost: 150 Coins, 30 Logs`, `Build time: 2m` (`DurationText`), `Max workers: 3`, the recipe `2 Logs → 1 Planks · 60/h at 3 workers` (the rate is `ProductionDisplay.PerHour`, so research shows in it), the lock `Requires: Trade Charter` (a locked card is disabled and cannot be selected) and one hint (`All builders are busy`, then `Not enough <items>`; the server's order). `BuildMenuModel.Update` follows `DisplayCity.Current` once a second; hints never stop a selection, the server decides. `TryToggle` selects a card (a second tap clears it); placing is M0-46. A press over the menu belongs to the UI: `CityWorld.IsPointerOverUi` (set to `BuildMenu.IsOverUi`, which asks the panel) keeps it from panning, tapping or hovering the ground. The menu's root is padded by `Screen.safeArea` (`SafeAreaInsets`). How to add a screen: `docs/how-to/add-ui-screen.md`.
- **Feedback (M0-47):** every command result is shown as a toast, from one place. `CommandSender.Completed` fires once for each intent that ended with the server's answer or an error (not for a replaced worker target); `CommandFeedback` listens to it and adds a toast to the `ToastQueue`, which `ToastHost` draws stacked at the bottom left, above the status label and the buttons (its own `UIDocument`, sort order 3, no label takes the pointer). A success says what started ("Construction started", "Upgrade started", "Workers updated", "Research started"); a failure says the sentence `FeedbackMessages` has for its error code ("All builders are busy", "Research needed first", "Not enough free workers. Build more housing"), a lost connection or a timeout says to check the network and try again, a rate limit names the wait the server gave. **A test fails when a code of `ApiErrorCodes` has no sentence** (it lists the constants by reflection), and `ClientErrorCodesTests` holds `ApiErrorCodes` to the table of `05`. No sentence holds a game number or a content name. The code, status and trace id of a failure go to the log as a warning, never to the screen; a stack never does. At most three toasts show at once, an error stays 5 s, a success 2.5 s, and the same words shown again renew the toast instead of stacking. A screen that sends a command needs no toast code of its own; one that needs a sentence for a new command adds it to `FeedbackMessages.ForSuccess`.
- **HUD (M0-49):** `HudView` (its own `UIDocument`, sort order 0.5, so the menu, the bar and the toasts draw over it; layouts `UI/Hud` and `UI/HudChip`) shows the top of the screen from `HudModel`, which follows `DisplayCity.Current` and the monitor's `ConnectionState` once a second and raises `Changed` only when a value differs. One `ItemChipModel` per item of the city's era or an earlier one, in the content's order: the item's icon (`UiIcons.ForItem`; the item's first letter only when there is no picture), the stock, the cap when the item has one (`CityQueries.TryGetEffectiveCap`, research bonuses included) and the net rate per hour from `ProductionDisplay.NetPerHour` worded by `PerHourText` (`+60/h`, `−30/h`, `0/h`; one tenth when not whole, rounded toward zero). Then workers free / provided and builders busy / slots (`Rules.BuilderSlots`), each with its icon beside the number, the research ring (`ProgressDisplay.ResearchProgressPermille` at the displayed clock, the node's name, the time left; the research icon sits in its middle) or `No research`, the era badge (the era's name from the content) and the connection indicator (a dot and a word: `Online`, `Connecting`, `Offline`, `Signed out`, `Update needed`, `Server problem`). The long status sentence with the error code stays in `ConnectionStatusView`, now at the bottom left; the toasts start below the HUD. No element of the HUD takes the pointer.
- **Connection states (M0-55):** the city stays on screen in every state, predicted from the last snapshot. **One rule for every command button:** `CommandAvailability.For(state)` allows a command only when `Connected`; in any other state the stepper's − and +, Upgrade, Finance and Place are off and their note is the reason (`You are offline`, `The server has a problem`, `Signed out`, `Update needed`, `Connecting…`), before any other reason. `GameRoot` hands it to the placement model, `InspectorFlow` and `ResearchFlow` whenever the connection changes, and a press that still arrives sends nothing. It is a hint (the server checks again), and the one case where the client switches a button off for a command the server might accept. What is on its way stays: the pending worker target and research keep showing and the sender keeps sending; the build cards stay selectable (they send nothing). `ConnectionBanner` (its own `UIDocument`, sort order 4, above the toasts; layout `UI/ConnectionBanner`) shows, for `Offline`, `ServerError` and `Unauthorized`, a strip under the HUD: one line (`Offline. The city shown may be out of date.`), `Last synced 3m ago` (`SyncAgeText`: `just now`, `45s ago`, `3m ago`, `1h 5m ago`; from `ClientCityStore.WholeSecondsSinceReceived`, so a command's answer counts as a sync) and one button: `Try again`, or `Sign in again` for `Unauthorized`. The button asks the monitor for a poll (`ConnectionFlow`), which includes the one new login after a refused token; it reads `Trying…` and is off until `PollFinished`. For `IncompatibleVersion` a full-screen scrim (it takes the pointer over the whole screen) says `Update needed` and that the game does not match the server, with `Check again`. `ConnectionBannerModel` holds every sentence; `ConnectionFlow` refreshes it on a state change, a snapshot and each second.
- **Placement (M0-46):** a card picked in the menu starts `PlacementFlow` (`PlacementFlowModel`: `Idle` → `PickingTile` → `Confirming` → `Sending`) and closes the sheet; the ground paints every tile green (free) or red (occupied) from the displayed city (`GroundTiles.ShowHints`; a red tile can be tapped, and the bar says "This tile is occupied", but **Place** stays dimmed and nothing is sent for it; the server still checks every command); a tap picks the tile, and the `PlacementBar` (bottom right, its own `UIDocument`) asks "Build Cottage at (3, 4)?" with **Place** and **Cancel**. **Place** gives `CommandSender.SendAsync` a `PlaceBuilding` intent; while the request is open (retries included) `PlacementGhosts` draws a translucent copy of the type on the tile for every `PlaceBuilding` in `CommandSender.Pending`, and nothing else changes: no coins subtracted, no building. A success puts the real building on screen from the new snapshot, removes the ghost in the same call and ends the flow; a refusal removes the ghost, shows its human message (`FeedbackMessages`, M0-47; never the code) in the bar, keeps the card and drops the tile. **Cancel**, or tapping the card again, ends the flow at any step before **Place**; a sent command cannot be cancelled. While one is on its way the picks are frozen.
- **The start (`StartupFlow`):** a kept token refused by `GET /content` or by `GET /city` gets one new login and one repeat; a refusal after a fresh login is a failure.
- **The wire:** no redirect is followed, because the API never sends one and the bearer token must go to no one else (CR-0004).

## UX rules
- **One menu at a time (owner directive OD-16, `15`).** The screens the player opens and closes (the build menu's sheet, the building inspector, the research screen, the welcome-back report, and every later one) are one `MenuGroup`: when one opens, the others close. A menu joins the group in `GameRoot` with the action that closes it, and tells the group when it goes from closed to open (an `Opened` event). Its close action must be safe when the menu is already closed, and must not drop state that belongs to another flow (the inspector closes by dropping the tile only while it is shown, because the placement flow owns the tile while it runs). The placement bar and the toasts are not menus: they belong to a flow or to a result.
- No optimistic economy: never subtract resources, change worker counts or spawn a finished building
  before the server confirms. A "pending" ghost or a pending stepper value is fine.
- The worker stepper sends the **absolute** target count after a short debounce (~400 ms), so rapid taps
  become one command.
- Client-side checks (tile occupied, obviously unaffordable, no free workers, research locked) are
  **UX hints only**; the server re-checks.
- Every error code maps to a human message (`FeedbackMessages`, M0-47; a test fails for a code without one). Nothing is shown only in logs, and no code, server text or stack is shown to the player.
- Touch targets ≥ 48 dp; respect `Screen.safeArea` on the UI root. **One panel unit is about one dp on a landscape phone:** `UI/PanelSettings` scales with the screen, matched on its height, reference 880 × 400 (CR-0007), so a button that is 48 units high is a 48 dp touch target and a screen is about 400 units tall and 700 to 890 wide. (It was `ConstantPhysicalSize` before, one unit a 96th of an inch on the device's own density, which made every screen physically huge on a phone.)
- **One look (CR-0007).** Every layout imports `UI/Common.uss`: the tokens (wood and parchment colours from the Era I palette, five font sizes, a spacing scale, the radius, `--touch` 48, `--hud-height`, `--dock-width`) and the shared classes (`t-*` text, `panel-wood`, `panel-parchment`, `scrim`, `btn` with `btn--primary`, `btn--danger` and `btn--quiet`, `themed-scroll`). A screen's own stylesheet only says where things sit, and writes no colour and no font size (`SharedLookTests` fails for one, for a button without `btn`, for a layout without the import and for an undefined token). Wood is the HUD and the build tray, parchment is every panel the player reads; green is go, amber a warning, red stop. The screens under the HUD start at `--hud-height`. Painters in C# (the HUD and research rings) take their colours from the same palette by hand, because a painter cannot read a token.
- Art and labels are era-aware from the start: look up building visuals by `(typeId, era, level)` (`BuildingLooks`), even though M0 has only Era I.

## Shared-code constraints (C# 9, netstandard2.1)
No file-scoped namespaces, no global usings, no `required`, no records or `init` without an
`IsExternalInit` shim. Put `#nullable enable` at the top of shared files.

## Running tests from the CLI
`Unity -batchmode -projectPath client/CityBuilder -runTests -testPlatform EditMode -testResults <file>`
The Editor must be closed for that project (project lock). `scripts/dev/test-unity.sh` (and `.ps1`) wraps this for EditMode then PlayMode: it reads the
Unity program from `UNITY_EDITOR`, prints a summary and exits non-zero on a failure or when no test ran (`client/README.md` → Run the tests).

## Device testing
Android device → server on your PC: use the PC's LAN IP or `adb reverse tcp:8080 tcp:8080`.
IL2CPP may strip DTO members used only via reflection: add a `link.xml` preserving the DTO assembly.
