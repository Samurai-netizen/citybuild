## Authentication
- Every `/api/v1/` endpoint except the dev login requires `Authorization: Bearer <accessToken>`. The acting player comes only from the
  token; no body carries a player id. A missing, malformed, expired or wrongly signed token gets 401 with the Problem Details body
  below (`code` `AUTHENTICATION_REQUIRED`) and `WWW-Authenticate: Bearer`. So does a signed token that names no player, and, on a request that
  reads the city, a token whose player has no city (a reset development database, CR-0004). The answer is the same for every kind of refusal and
  never says why a token was refused.
- `POST /api/v1/auth/dev-login` exists only in Development with `Auth:DevLoginEnabled` on; elsewhere the path is 404. Body
  `{ "displayName": "dev1" }`: 1 to 32 ASCII letters, digits, `_`, `-` or `.`, compared exactly. Answer 200
  `{ "accessToken": "eyJ…", "expiresAtUtc": "2026-10-27T21:00:00+00:00" }` for a new and a known name alike. A missing body or a name that
  isn't allowed → 400 `INVALID_ARGUMENT`. Like every body, it may hold no other property (400, M0-30).
- The token is a JWT (HMAC-SHA256) whose `sub` is the player id; it lives `Auth:TokenLifetimeMinutes` (12 h by default). The client logs in
  again when it expires. Details: `07-security-model.md`, `docs/modules/CityBuilder.Api.md`.

## Request limits (every request)
- **Body size:** no body larger than `RequestLimits:MaxBodyBytes` (4096 bytes by default, 1024 to 1 MiB, checked at startup) is read. A
  request whose `Content-Length` is larger gets 400 `INVALID_ARGUMENT` before anything else, the token check included; Kestrel stops
  reading any other body at the limit, and the answer to that stop (Kestrel ends the request with an empty 413) is rewritten to the same 400 `INVALID_ARGUMENT` (M0-34).
- **JSON:** a body is sent as `application/json` (anything else is 415, also a body with no `Content-Type`), and it names each property once: a property twice, also in
  another case, is refused with 400 instead of read as its last value.

## Response headers (every answer)
`Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and no `Server` header (CR-0004). `/health` takes GET and HEAD; any other method is 405.

## Content (`GET /content`)
One document, the same for every player: `contentVersion`; `rules` (`gridWidth`, `gridHeight`, `builderSlots`, `researchSlots`,
`baseStorageCaps`, `maxOfflineProductionSeconds`, `minCycleSeconds`, `maxLaborReductionPermille`, `timeScale`); `startingCity` (`era`,
`inventory`); `eras`; `items`;
`buildings`, each with its `levels` (`maxWorkers`, `workersProvided`, `recipe` with `inputs`, `outputs` and `labor`, `upgradeCost`,
`upgradeSeconds`); and `research` (`cost`, `durationSeconds`, `prerequisites`, `effects`). The numbers are the content file's.
- **Order:** eras by number; items, buildings, research and prerequisites by id (ordinal); levels by level. Item maps (costs, recipe sides,
  caps) are JSON objects from item id to quantity with keys in ordinal order. The same content gives the same text on every call.
- **Nulls are written, never left out:** a house's `recipe`; `upgradeCost` and `upgradeSeconds` of level 1 (it is built, not upgraded to);
  `unlockedBy` of a building that needs no research. `maxWorkers` is 0 for houses and `workersProvided` is 0 for producers.
- **Names:** `kind` is `House` or `Producer`. An effect is one flat object: `type` (`unlockBuilding`, `laborReduction`, `storageCapBonus`)
  and the fields that type uses (`building`, `permille`, `item`, `amount`); the other fields are `null`.
- `rules.timeScale` is the server clock's speed: server seconds per real second. Always 1 outside Development; a Development server with
  `Simulation:DevTimeScale` above 1 reports that scale (M0-35, `04` §1).
- **CR-0008:** `rules` has `groundTileMillis`, `crossingSpeedPermille`, `minWalkSeconds` and `maxWalkBonusPermille` (before `timeScale`),
  and the document ends with `roads`, the road levels by level (`level`, `name`, `tileMillis`, `cost`: to place at level 1, to upgrade to it
  above) (built, CR-0008-T1 part C). *Planned, the part that builds each:* `rules` loses `baseStorageCaps` (part E) and
  `maxOfflineProductionSeconds` (part H) and gains `tripCarryLimit`, `maxRouteStops`, `maxStopActions`; a top-level `amountPresets`
  (`id`, `name`, `percent`);
  an item's `capped` becomes `currency`; `startingCity.inventory` becomes `startingCity.purse`; `kind` adds `Warehouse`, `CourierStation`
  and `Science`; a building may have `maxPerCity`; a level adds `storage` (good → limit), `carryLimit` and `staminaSeconds`; effects add
  `unlockAmountMode` (`mode`: `percent` or `exact`) and `walkSpeedBonus` (`permille`). The same rules for order and nulls apply.
- **Complete for the client:** the client builds its `GameContent` from this document with the engine's validating factory, as the server does
  from its file. So the document holds everything the factory needs (`startingCity` included), under the content file's property names.
  The differences are the response's: `kind` is `House` or `Producer` (the file has `house`, `producer`), and it adds `unlockedBy` and `timeScale`,
  which the factory ignores. A test rebuilds the content from the response and gets the same response back.

`GET /city` is safe to repeat but **not side-effect free**: it materializes elapsed time ([ADR-0005](../docs/adr/ADR-0005-settle-on-access.md)).
There is no "claim" command, because production and research complete on their own.

## Commands (`POST /commands/*`)
- **The body is the contract, exactly.** Every field is required; a property the body doesn't define (`cost`, `level`, `workers`,
  `playerId`), a missing field, a number sent as a string, a bad GUID or broken JSON is refused with 400 before anything runs. No body or
  JSON `null`, the all-zeros `requestId`, an id that can't be a content id (blank, over 64 characters, anything but lowercase ASCII
  letters, digits and `_` after a first letter: a type id or a research id), a building id below 1, a negative coordinate and a negative worker count are `INVALID_ARGUMENT`, before the city
  is locked or settled: no city and no content could make them valid (owner directive OD-13 in `15`). The binding's own refusals (unknown, missing
  or mistyped fields, broken JSON) are the same 400 `INVALID_ARGUMENT` in every environment (M0-34).
- **Success:** 200 with the snapshot below; its `requestId` is the command's. A replay (same `requestId`, same body) gets 200 with the
  stored snapshot, byte for byte, even when the city has changed since.
- **Refusal:** Problem Details with the code's status from the table below, `code`, and `requestId` when the request had one. A rule's
  refusal commits the settlement of the elapsed time but stores no receipt (Idempotency rules).
- `place-building` (`{ requestId, buildingTypeId, x, y }`) checks in the order of `04` §8: `UNKNOWN_BUILDING_TYPE`, `BUILDING_LOCKED`,
  `OUT_OF_BOUNDS` (past the grid's width or height; a negative coordinate is `INVALID_ARGUMENT`), `TILE_OCCUPIED`, `NO_FREE_BUILDER`, `INSUFFICIENT_RESOURCE`. It pays the type's cost (`COST_PLACE` ledger rows) and
  the building appears with the next id, level 1, `Constructing` until the clock plus the type's build seconds.
- `upgrade-building` (`{ requestId, buildingId }`) checks in the order of `04` §8: `BUILDING_NOT_FOUND` (the id is looked up in **your**
  city only; ids count from 1 in each city, so one only another city has is not found; below 1 is `INVALID_ARGUMENT`), `BUILDING_BUSY`
  (constructing or upgrading), `MAX_LEVEL`, `NO_FREE_BUILDER`, `INSUFFICIENT_RESOURCE` (the stock before any refund). A running or frozen
  cycle ends without output and its inputs come back (`REFUND_UPGRADE` rows, even above a storage cap); then the next level's upgrade cost
  is paid (`COST_UPGRADE` rows) and the building is `Upgrading` until the clock plus that level's upgrade seconds, still at its level. Its
  workers stay assigned and do nothing (`maxWorkers` stays the current level's); at the end the level rises and the building is `Idle` with
  the same workers (a producer starts its next cycle when it can); the new level's max workers and workers provided apply from then on.
- `assign-workers` (`{ requestId, buildingId, workers }`, an absolute count; 0 pauses) checks in the order of `04` §8: `BUILDING_NOT_FOUND`
  (your city only, as above; an id below 1 is `INVALID_ARGUMENT`), `INVALID_ARGUMENT` (a house: no recipe), `BUILDING_BUSY` (constructing;
  upgrading is allowed), `WORKER_LIMIT` (above the current level's `maxWorkers`; a negative count is `INVALID_ARGUMENT` before the lock),
  `INSUFFICIENT_WORKERS` (the increase over the building's current count is more than `workers.free`; fewer workers always fit). It writes no
  ledger rows. On a running cycle the labor done so far is kept (`04` §3): a new segment starts at the clock with `laborRemaining` reduced
  by it, and `phaseEndsAt` is the clock plus `ceil(laborRemaining / workers)`, or `null` with 0 workers (`stallReason` `NoWorkers`) until a
  later assignment resumes it. An idle producer that can start begins its cycle in the same response. The same count again succeeds and
  moves nothing a player sees (the end, the progress); like every successful command it is saved, so `stateVersion` rises.
- `start-research` (`{ requestId, researchId }`) checks in the order of `04` §8: `UNKNOWN_RESEARCH` (an id of the content-id form the content
  doesn't have; any other text is `INVALID_ARGUMENT` before the lock), `RESEARCH_COMPLETED`, `RESEARCH_IN_PROGRESS` (the one research slot
  is busy), `RESEARCH_LOCKED` (a prerequisite not completed, or the node is of another era than the city's), `INSUFFICIENT_RESOURCE`. It pays
  the node's whole cost up front (`COST_RESEARCH` ledger rows) and the snapshot's `research` block shows it running from the clock to the
  clock plus its `durationSeconds`. It completes on its own in the settle of a later request at that second, before any building completes
  then (`04` §5, §6): the node is added to `completed`, `settlement.completedResearch` names it, and its effects apply from that second (a
  building it unlocks can be placed; a labor reduction shortens the cycles that start from that second on, running cycles keep theirs; a storage bonus raises `storageCaps`).

- **CR-0008 changes**: `place-building` checks `TILE_OCCUPIED` also for a road (built, CR-0008-T1 parts C and D). *Planned (part E):* it
  checks `BUILDING_LIMIT` (the type's `maxPerCity`) before `NO_FREE_BUILDER`; it pays only the cost's coins, and the building is a construction site (`phaseEndsAt` `null`, `needs` the cost's
  goods) until walkers have delivered them, then constructs. `upgrade-building` pays only the coins; without goods in the upgrade cost it
  starts at once as above, otherwise the building keeps working with `project` `Upgrade` and `needs` until the last good arrives, then the
  upgrade starts (refund, `Upgrading`). `start-research` checks `NO_SCIENCE_BUILDING` (no completed science building) before
  `INSUFFICIENT_RESOURCE`, pays the coins, and the research waits (`startedAt`, `endsAt` `null`, `needs`) until its goods reach the science
  building. `assign-workers` also takes a courier station (its workers are couriers).
- **Amounts** (CR-0008) are one JSON string: a preset id (`"all"`, `"half"`, `"quarter"`), a percentage (`"1%"` … `"100%"`) or an exact
  number (`"1"` … 12 digits, no leading zero). Any other text, and a percentage outside 1–100, is `INVALID_ARGUMENT` before the lock; an
  unknown preset id is `INVALID_ARGUMENT` from the rule; a mode the city hasn't researched is `AMOUNT_MODE_LOCKED`.
- `place-roads`, `upgrade-roads`, `remove-roads` (`{ requestId, tiles: [{ x, y }] }`, CR-0008-T1 part D): 1 to 64 tiles, each once,
  coordinates ≥ 0, else `INVALID_ARGUMENT` before the lock (a JSON `null` tile or list too). All or nothing, each check over the whole list
  in the order of `04` §8: placing checks `OUT_OF_BOUNDS`, `TILE_OCCUPIED` (a building or a road), `INSUFFICIENT_RESOURCE` (the coins of
  level 1 per tile; `COST_ROAD` ledger rows); upgrading `ROAD_NOT_FOUND` (also past the grid's edge), `MAX_LEVEL`, `INSUFFICIENT_RESOURCE`
  (each tile's next level's coins; `COST_ROAD` rows); removing `ROAD_NOT_FOUND`, and refunds nothing (no ledger rows). No builder slot, and
  the roads are there in the same response. The tiles' order is part of the payload: a retry sends them in the same order.
- `start-trip` (`{ requestId, sourceId, targetId, itemId, amount }`, *(planned, part E)*): ids ≥ 1 and different, an item id of the
  content-id form, an amount as above, else `INVALID_ARGUMENT` before the lock. Then `BUILDING_NOT_FOUND`, `UNKNOWN_ITEM`,
  `INVALID_ARGUMENT` (the currency, an unknown preset), `AMOUNT_MODE_LOCKED`, `ITEM_NOT_ACCEPTED`, `INSUFFICIENT_WORKERS`,
  `NOTHING_TO_CARRY`. A free worker takes the goods at once (at most `tripCarryLimit`) and appears in `trips` until it arrives (`04` §18).
- `set-route` (`{ requestId, stationId, slot, stops: [{ buildingId, actions: [{ kind, itemId, amount }] }] }`, *(planned, part G)*): ids
  and `slot` ≥ 1, 0 to 16 stops, 1 to 8 actions per stop, `kind` `take` or `put`, item ids of the content-id form, amounts as above, else
  `INVALID_ARGUMENT` before the lock. Then `BUILDING_NOT_FOUND`, `INVALID_ARGUMENT` (not a courier station; the currency; an unknown
  preset), `INVALID_ROUTE` (slot above the station level's courier limit, 1 stop or more than `maxRouteStops`, more than `maxStopActions`, two
  consecutive stops at one building), `UNKNOWN_ITEM`, `AMOUNT_MODE_LOCKED`. 0 stops clears the route.
- `reenergize-couriers` (`{ requestId }`, *(planned, part H)*): always succeeds; every courier's stamina is full again and resting ones leave.

## Snapshot (every successful city/command response)

```json
{
  "requestId": "6f1c…", "stateVersion": 42, "serverTimeUtc": "2026-10-03T10:30:05Z", "contentVersion": "mvp-1",
  "city": {
    "clock": 123456, "era": 1,
    "inventory": { "coins": 640, "logs": 37, "planks": 12 },
    "storageCaps": { "logs": 750, "planks": 750 },
    "workers": { "provided": 8, "assigned": 7, "free": 1 },
    "builders": { "slots": 2, "busy": 1 },
    "research": { "activeId": "frame_saw", "startedAt": 120000, "endsAt": 123600,
                  "completed": ["sharp_axes", "storehouses", "trade_charter"] },
    "buildings": [
      { "id": 4, "typeId": "sawmill", "x": 2, "y": 4, "level": 1,
        "assignedWorkers": 3, "maxWorkers": 3, "phase": "Producing",
        "phaseStartedAt": 123420, "phaseEndsAt": 123480,
        "cycleLabor": 180, "laborRemaining": 180, "segmentStartedAt": 123420, "stallReason": null }
    ],
    "roads": [ { "x": 2, "y": 5, "level": 1 }, { "x": 3, "y": 5, "level": 2 } ]
  },
  "settlement": { "elapsedSeconds": 36000, "productionSeconds": 28800,
                  "produced": { "logs": 960 }, "consumed": { "logs": 940 },
                  "completedBuildings": [7], "completedResearch": ["frame_saw"], "eraChanged": false }
}
```

- `requestId` is the command's, and `null` on `GET /city`, which is no command. `serverTimeUtc` is the server time of the request in whole
  seconds, UTC, with a literal `Z`. `stateVersion` is the stored version after the request: it rises only when the request changed the city.
- `inventory` lists the items the city holds (an item it has none of is absent); `storageCaps` lists every capped item with its cap now (base
  plus research). `maxWorkers` is the most workers the building's current level takes, also while it is being built or upgraded (0 for houses).
  `phase` is `Constructing`, `Upgrading`, `Idle` or `Producing`; the timer fields a phase doesn't use are 0.
- `settlement` is what the settlement **of this request** did, from the city's last settled second to now: a request seconds after another
  one reports only those seconds. The client reads it on every snapshot it takes (`SettlementSummary`); a settlement of 300 seconds or more
  (a routine poll settles about 120) is shown to the player as the welcome-back report (`09`).
- `stallReason` is one of `null`, `"NoRecipe"`, `"NoWorkers"`, `"MissingInput:logs"` or `"StorageFull:planks"`. `phaseEndsAt` is `null` for a frozen cycle.
- Lists are sorted: buildings by `id`, completed research by `id` (ordinal), roads by `x`, then `y`.
- `roads` lists every road tile with its level (CR-0008-T1 part D); a new city has none (`[]`).
- Progress for display: `done = cycleLabor − (laborRemaining − (clientClock − segmentStartedAt) × assignedWorkers)`.
- **CR-0008** *(planned: part E unless named)*: `city.inventory` and `storageCaps` are replaced by `purse` (the coins) and `totals` (every
  item's city total: stores, loads, the purse); `workers` adds `onTrips`; `research` adds `needs` (item → still missing; `startedAt` and
  `endsAt` are `null` while it waits); each building adds `store` (good → quantity, only goods it holds), `storeLimits` (good → effective
  limit) and `needs`, and `project` (`null`, `"Construction"` or `"Upgrade"`); `roads` (built, part D, above); `trips` (`id`,
  `sourceId`, `targetId`, `itemId`, `quantity`, `departedAt`, `arrivesAt`); `couriers` (`stationId`, `slot`, `state` `AtStation` ·
  `Walking` · `Returning` · `Resting`, `toStop` (1-based, 0 unless walking to a stop), `departedAt`, `arrivesAt` (`null` at the station),
  `stamina`, `load` [`itemId`, `fromId`, `quantity`], part G; stamina part H); `routes` (`stationId`, `slot`, `stops` as `set-route`
  sends them, part G). Lists sorted: roads by (`x`, `y`), trips by `id`, couriers and routes by (`stationId`, `slot`), loads by (`itemId`,
  `fromId`). `settlement` loses `productionSeconds` (part H) and adds `delivered`, `moved`, `refunded` (item maps, part E),
  `courierSeconds` and `tiredCouriers` [`stationId`, `slot`, `at`] (part H). `stallReason` keeps its values; a courier station without
  couriers is `NoWorkers`, a warehouse or science building `NoRecipe`.
- `clientClock = city.clock + secondsSinceSnapshotReceived × rules.timeScale`. `timeScale` is in `GET /content` and is always 1 outside Development.

## Errors: RFC 9457 Problem Details with a stable `code`

```json
{ "type": "urn:citybuilder:error:insufficient-resource", "title": "Not enough resources",
  "status": 422, "code": "INSUFFICIENT_RESOURCE", "detail": "Need 20 planks, have 12.",
  "traceId": "00-…", "requestId": "6f1c…" }
```

| Code | HTTP | When |
|---|---|---|
| `AUTHENTICATION_REQUIRED` | 401 | Missing, invalid or expired token, or a token whose player has no city: log in again |
| `INVALID_ARGUMENT` | 400 | Malformed JSON, unknown or missing field, bad GUID, body too large, a value no city could make valid (OD-13: a building id below 1, a negative coordinate, a negative worker count, a type, research or item id that can't be a content id, an amount of none of the three forms), workers on a building that takes none (a house, a warehouse, the science building), a trip to its own source or with the currency, an unknown amount preset (CR-0008) |
| `UNKNOWN_BUILDING_TYPE` | 422 | Type id not in content |
| `BUILDING_LOCKED` | 422 | Type of a later era than the city's, or not unlocked by research yet |
| `OUT_OF_BOUNDS` | 422 | Coordinates past the grid's width or height (negative ones are `INVALID_ARGUMENT`) |
| `TILE_OCCUPIED` | 409 | Tile already has a building (from CR-0008 also a road) |
| `INSUFFICIENT_RESOURCE` | 422 | Cost not affordable (from CR-0008: its coins; goods are delivered later) |
| `INSUFFICIENT_WORKERS` | 422 | Not enough free workers for the requested assignment (from CR-0008 also for a trip) |
| `WORKER_LIMIT` | 422 | Requested workers above the building's max for its level (a negative count is `INVALID_ARGUMENT`) |
| `NO_FREE_BUILDER` | 409 | All builder slots busy |
| `BUILDING_NOT_FOUND` | 404 | Id not in **your** city (also returned for other players' ids) |
| `BUILDING_BUSY` | 409 | Upgrade: building is constructing or upgrading. Assign workers: building is still constructing |
| `MAX_LEVEL` | 422 | Already at max level |
| `UNKNOWN_RESEARCH` | 422 | Research id not in content |
| `RESEARCH_LOCKED` | 422 | Prerequisites missing or the node belongs to another era |
| `RESEARCH_IN_PROGRESS` | 409 | The research slot is busy |
| `RESEARCH_COMPLETED` | 409 | Already researched |
| `ROAD_NOT_FOUND` | 404 | A tile of the list has no road (CR-0008) |
| `BUILDING_LIMIT` | 422 | The city already has the most buildings of the type, `maxPerCity`: the science building (CR-0008) |
| `NO_SCIENCE_BUILDING` | 422 | Research needs a completed science building (CR-0008) |
| `UNKNOWN_ITEM` | 422 | Item id not in content (CR-0008) |
| `AMOUNT_MODE_LOCKED` | 422 | A percentage or exact amount before the research that unlocks it (CR-0008) |
| `ITEM_NOT_ACCEPTED` | 422 | The trip's target neither needs the item for a project nor stores it (CR-0008) |
| `NOTHING_TO_CARRY` | 422 | The trip's amount gives nothing: the source holds none of the item (CR-0008) |
| `IDEMPOTENCY_CONFLICT` | 409 | Same `requestId`, different payload |
| `RATE_LIMITED` | 429 | Too many requests |
| `CONCURRENCY_CONFLICT` | 409 | Lock timeout or version mismatch; safe to retry |
| `INTERNAL_ERROR` | 500 | Anything unexpected; no stack traces in responses |
| `NOT_FOUND` | 404 | A path no endpoint has (also the dev login outside Development) |
| `METHOD_NOT_ALLOWED` | 405 | A method the endpoint doesn't take |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | A body that isn't `application/json`, or has no `Content-Type` |
| `UNSUPPORTED_CLIENT_VERSION` | 426 | The `X-Client-Version` build is no longer supported; update the game. *Reserved (M0-58): the server refuses no build yet.* The client treats it as `IncompatibleVersion` |

**Planned code (CR-0008).** It joins the table above (and the catalogue, the client's `ApiErrorCodes` and `FeedbackMessages`) in part G of
CR-0008-T1: `INVALID_ROUTE` 422 (a route's slot, stop count, action count or consecutive stops break the content's route rules).

`code` is for program logic. `title` and `detail` are for humans and may change. `traceId` names the HTTP request (W3C trace context, always
the server's own: a `traceparent` the client sends is ignored, M0-60; its second part is the `TraceId` of every log line of the request),
`requestId` the command across its retries: `docs/api/logs-and-correlation.md`.

- One writer, one list: every code above is a member of `ErrorCatalogue` (`CityBuilder.Api/Errors/`), and `ApiProblem` writes every error answer
  with exactly these members: `type` (`urn:citybuilder:error:` and the code in kebab case), `title`, `status`, `detail`, `code`, `requestId` **only
  when the request had one** (an answer to `GET /city`, a request that could not be read, a rate limit and a 500 have none) and `traceId`.
  A test holds every code to this table and to a source that produces it, and `ClientErrorCodesTests` holds the Unity client's `ApiErrorCodes` to the same table. The client turns each code into a human sentence in `FeedbackMessages` (M0-47), and a client test fails for a code without one, so a new code needs its sentence there.
- **No stack trace in any response, in any environment.** An unexpected exception is 500 `INTERNAL_ERROR` with the catalogue's detail; only in
  Development does `detail` also name the exception's type and message. The exception and its stack are logged (event id 3000).
- A request that can't be read at all (broken JSON, a field the contract doesn't have, a body that doesn't bind) is 400 `INVALID_ARGUMENT` in
  Development and Production alike; the answer never echoes the request or its headers.
- **Every error answer has a `code`**, also the three the framework ends without a body (`NOT_FOUND`, `METHOD_NOT_ALLOWED`,
  `UNSUPPORTED_MEDIA_TYPE`): the status code pages give them the catalogue's Problem Details. A body Kestrel stops at the size limit (an empty 413 inside
  the binding) is rewritten to 400 `INVALID_ARGUMENT`. (M0-34, owner's delegated decision 3: add the three codes.)
- `CONCURRENCY_CONFLICT` and `RATE_LIMITED` are retryable: the first with the same `requestId` at once, the second after `Retry-After`. The Unity client's `CommandSender` (M0-40) repeats `CONCURRENCY_CONFLICT` after its normal wait and leaves `RATE_LIMITED` to the player.

## Idempotency rules
- `requestId` is a client-generated UUID, required on every command, and reused on every retry.
- Receipts are stored for **successful** commands only, keyed by `(playerId, requestId)`, with a SHA-256 hash of the
  canonical payload. Same id + same hash → the stored response, with no re-execution.
- Business-rule rejections are not stored. The player's next attempt uses a new `requestId`.
- Another player's `requestId` never matches yours, because the key includes `playerId`.
- The canonical payload is the command type, a line break, and the command's data as JSON with its properties in ordinal name order
  (`CommandPayload`, decision 042 in `12`). The same `requestId` on another command is a conflict as well.
- A replay returns the stored response text byte for byte (decision 041 in `12`) and runs nothing, not even the settle; a conflict neither.
- An empty `requestId` (all zeros) is `INVALID_ARGUMENT`, like any other wrong shape: refused before the database.

## Rate limits (per player, built-in ASP.NET Core limiter)
A request over a limit is refused with 429 `RATE_LIMITED`, a `Retry-After` header in whole seconds (at least 1, at most the window's length: the
time after which the player is sure to have a new budget) and the Problem Details body, before the body is read or a city is locked.
Fixed windows, in memory, one process; the numbers are configuration (`RateLimits:*` in `docs/getting-started.md`), their defaults are:

| Limit | Counted for | Default | Keys |
|---|---|---|---|
| Commands, burst | every command endpoint together, per player | 10 per second | `RateLimits:Commands:Burst:Limit`, `:WindowSeconds` |
| Commands, sustained | the same requests, per player | 120 per minute | `RateLimits:Commands:Sustained:Limit`, `:WindowSeconds` |
| `GET /city` | per player | 30 per minute | `RateLimits:City:Limit`, `:WindowSeconds` |
| `GET /content` | per player, a budget of its own | 30 per minute | `RateLimits:Content:Limit`, `:WindowSeconds` |
| Dev login | per remote address | 10 per minute | `RateLimits:DevLogin:Limit`, `:WindowSeconds` |

- A command must pass both command limits. Every request counts, also one the binding or a rule refuses, so a script that sends junk is
  limited too. A refused request counts nothing twice and a limited one is never bound or locked.
- The player is the token's `sub`; the limiter runs after the token check, so a request without a working token is 401 and counts for
  nobody. One player's spam never uses up another player's budget, and `GET /city`, `GET /content` and the commands have separate budgets.
- `GET /content` is limited too (M0-34, owner's delegated decision 6): it reads no city, but a loop on it costs the server CPU, and a client fetches it once per start and once per `contentVersion`, far below 30 a minute.
- A normal client is far below the defaults: a poll every few seconds is 12 to 30 a minute, a tap is one command. A limit is a value from
  1 to 1 000 000 and a window from 1 to 3600 seconds, or the start stops.
- Behind a reverse proxy the remote address is the proxy's until forwarded headers are configured *(planned, with the deployment)*; the
  dev login exists in Development only (`07`).

## Request headers
- `Authorization: Bearer <token>` on everything except the dev login.
- `X-Client-Version: <build version>` (M0-58), sent by the client on every request: the Unity `Application.version`, for example `0.1.0`, 1 to 32
  characters of ASCII letters, digits, `.`, `-`, `+` and `_`. The server logs it (`ClientVersion` in the log scope of the request, `docs/api/logs-and-correlation.md`)
  and refuses nothing over it yet; a missing or unusable header is logged as `none` or `invalid`. Rejecting unsupported builds is a later task.
- No other header is read by the API beyond `Content-Type` and `Content-Length`: `traceparent`, `tracestate` and `baggage` are ignored. The
  full list of what a client sends, and what reads it: `07` → What the client sends.

## Versioning
Breaking changes → `/api/v2`. Content changes → a new `contentVersion`; the client refetches `/content`
when the snapshot's `contentVersion` differs from what it has. Market and guild endpoints (M2) will live
under `/api/v1/market/*` and `/api/v1/guilds/*` and use the same command pipeline.
