## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | Branch `task/M0-11-golden-scenario-1`; four steps as in the plan | one step for the whole task | each step is small and ends green; the split check is its own behaviour | local |
| 2 | The frozen file is an exact copy, `contentVersion` `mvp-1` included; it is never edited. A content change that should reach the golden scenario gets a new file (`content-golden-v2.json`) and hand-checked expectations | renaming the version inside the copy (`golden-1`) | the spec says copy; an exact copy shows which content release the table was checked against | local |
| 3 | `GoldenContent` reads the file with System.Text.Json (part of .NET 10, no package) and the same strict options as the server's `ContentFileLoader`, then `GameContentFactory` via `ContentAssert.Valid` | referencing `CityBuilder.Infrastructure` to reuse the loader; building the data in code | the reference would pull EF Core and Npgsql into the engine's test project and couple it to a server layer; data in code wouldn't be the frozen file the spec asks for. The cost is five duplicated option lines, with a comment naming their source | local |
| 4 | The file is read from the source tree (`RepositoryPaths.Root`), not copied to the build output | `CopyToOutputDirectory` in the csproj | one copy of the frozen file, no csproj change; the same helper already finds other repository files for tests | local |
| 5 | New folder `Golden/` for the runner and its tests (`Fixtures/` holds the JSON, as the spec says); the script lives in `GoldenScenario1`, the assertions in `GoldenScenario1Tests` | the script inside the test class | step 3 runs the same script with another step size; later golden scenarios get their own runner next to it | local |
| 6 | Each action runs as the server runs a command (settle to its time, the mutation must succeed, zero-length advance), like M0-10's `EngineRules/Commands`, but over the golden content. The table names no tiles, so the buildings stand in a row from (0, 0) | reusing `Commands` (bound to the synthetic `TestContent`); giving it a content parameter | `Commands` is two lines per command; a content parameter would touch every M0-10 test for no gain | local |
| 7 | One theory case per table row (`InlineData`: t, coins, logs, planks, free workers, buildings, research). Phase and stall reason are one text per building (`3 Producing`, `5 Idle MissingInput:planks`, ascending id) so a row reads like the table; the research state is checked at every row, not only at 600 | one assertion per building and field | a failure shows the whole row; checking research at every row costs nothing and also pins "active until 600" | local |
| 8 | The 750 row's "before placing: planks 20" is its own fact (`Before(750)`); the 150 row's "logs 12 → 10 at start" is not asserted as 12: the completion and the start happen in the same instant, and no settlement stops between them. The row's 10 logs with the Sawmill producing cover it | asserting the 12 through a settlement report | the report sums a whole advance, not a single instant; the end state is what the table promises | local |
