## Sessions

### Session 1 — 2026-11-01 · Claude Code / claude-sonnet-5-5
- **Plan:**
  1. `FeedbackMessages` (plain static class, `Presentation/Feedback/`): the one table from error code to a short human sentence (every member of
     `ApiErrorCodes`, plus `CLIENT_COMMAND_FAILED`), the success sentence of each `CommandKind`, a retry hint for `CLIENT_NETWORK_ERROR` /
     `CLIENT_TIMEOUT` / `CLIENT_INVALID_RESPONSE` / 5xx, a wait hint for `RATE_LIMITED`, and a generic fallback for a code the table lacks (never
     the server's `detail`, never a stack). EditMode tests, among them the completeness test: it lists the constants of `ApiErrorCodes` by
     reflection and fails for a code with no message.
  2. `ToastQueue` (plain class): the toasts on screen, from `Show(kind, text)` and a clock in whole seconds: expiry, a cap on how many show at once,
     an identical toast replaces its twin instead of stacking. EditMode tests.
  3. `ToastHost` (thin `MonoBehaviour`, own `UIDocument`, `UI/Toasts.uxml` + `.uss`): shows the queue's toasts at the top, never takes the pointer
     (so the ground below still gets the press), pads by the safe area. EditMode layout test as the other screens have.
  4. `CommandFeedback` (wiring): turns a `CommandOutcome` into a toast (success sentence, or the error's message); `PlacementFlow` gives it the
     outcome and the bar's error line uses the same message instead of `CODE: sentence`; `GameRoot` creates the host. PlayMode tests with the fake
     transport: place succeeds → success toast; refused → human message and no code; timeout → retry hint; a toast fades.
  5. Docs (the Docs impact table), `LOCAL-E2E.md` step 3 shows the toasts; finish.
- **Done:** step 0, write-ahead (this entry, the resume point, the board). Before it: the two `PlacementBar` `.meta` files that Unity completed on first
  import were committed on their own (`chore(M0-46): complete UI importer metadata`, owner's choice: option 1).

## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | The message table is `FeedbackMessages` in `Presentation/Feedback/`, keyed by the code strings of `ApiErrorCodes`; the completeness test lists `ApiErrorCodes`' constants by reflection, so a code added to the class without a message fails the test. `ClientErrorCodesTests` already holds `ApiErrorCodes` to the table of `05`, so the chain 05 → `ApiErrorCodes` → message is closed | The table in `Net`; a JSON file; `Dictionary` built at start | The words are presentation, not transport; a `switch` over constants needs no start-up and no allocation; the content-JSON rule is for game numbers, and these are words, not numbers | local |
| 2 | Two sentences differ from the spec's examples: `NO_FREE_BUILDER` says "All builders are busy" (not "Both", the builder count is content), and `INSUFFICIENT_WORKERS` says "build more housing" (not "a Cottage", the housing building is content and changes with the era) | The spec's literal words | Principle 8 and `09` (era-aware labels): a number or a building name typed into a sentence goes stale when the content does | local |
| 3 | Every command outcome that is not `Superseded` gives a toast, successes and failures alike. The bar's error line stays (it holds until the player acts, a toast fades) and shows the same message, no longer `CODE: sentence` | Toast only; bar line only | A toast is seen even when the bar is hidden (the worker stepper and research screens will have no bar); the bar keeps the reason next to the buttons the player must press again. The code and the trace id go to the log, not to the screen | local |
