- **Done:** write-ahead (branch, this entry, resume point, board; the rows of M0-53 and CR-0006-T2 are set to `Done`, their PRs are merged).
  Step 1, desk audit (read, not run; the Editor was open, so no Unity test has run yet). Found and fixed, each with a regression test:
  - **Welcome-back opened on almost every snapshot at scale 60.** Root cause: `WelcomeBackModel.ThresholdSeconds` (300) was compared with the settlement's *city* seconds, and M0-53 decision 2 assumed they could only come from real absence. At 60 times the speed any request 5 real seconds after the last settles 300, so the modal report kept opening and closing the other menus (OD-16). Fixed: 300 × `timeScale`.
  - **A command refused for an expired token waited for the next poll.** Root cause: `ConnectionMonitor.RequestPoll` documents exactly this use and nothing called it. Tokens last 12 real minutes at scale 60 (12 h at scale 1). Fixed: `GameRoot` passes command errors to `ConnectionMonitor.ReportCommandError`; the toast says `Session expired. Try again in a moment`.
  Read and found sound: the stepper (the store takes the snapshot before the sender drops the pending target, so no frame shows the old value; superseding drops and adds a target in one call, before any redraw), the ring after a worker change (`CyclePermille` counts labor, the mapper carries all its fields), stall reasons (derived from the displayed city every second), the research ring (`ActiveResearch` clears in the same advance), screens not rebuilding their buttons each second. A backward jump is possible in theory: the display lags the server by the answer's latency × scale plus the floor, so a slower answer after a quick one can land behind it (up to 60 × the latency difference). Not changed without evidence: `PredictionWatch` measures it in the run.
  Step 2: the [MANUAL] run in `docs/testing/LOCAL-E2E.md`, and `PredictionWatch` so the run leaves evidence in the Editor log.

| 3 | A command's refused token asks for a poll through a new `ConnectionMonitor.ReportCommandError(error)`, called by `GameRoot` from `CommandSender.Completed`; no automatic re-send of the command | Re-sending inside the sender; the monitor listening to the sender itself | The player sees the toast and decides; `CommandPolicy` says this refusal is final. An error argument is testable without a sender, and `GameRoot` is where services meet | local |
| 4 | The toast for `AUTHENTICATION_REQUIRED` reads `Session expired. Try again in a moment` | Keeping `Signed out. Log in again` | The game has no login screen and logs in by itself; the old sentence asks for something the player cannot do | local |
| 5 | A dev-only `PredictionWatch` (Core) reports to `Debug.LogWarning`: the clock going back, counters that fell, and a snapshot that differs from the engine run on the one before, with the cities as JSON. Compiled always, created when `Debug.isDebugBuild` | Parsing the server log; waiting for M0-57's client logging; only the owner's eyes | The task asks to record each mismatch with its JSON, and an AI coder can read `Editor.log`. One more `Advance` per snapshot costs nothing. A warning, not an error: the run's Console stays free of red | local |
| 6 | `DisplayCity.SnapshotReplaced` hands the watch the city shown until then | Subscribing the watch to the store first; a copy of the city kept by the watch | Subscription order would be fragile; `Current` is replaced, not changed, so handing it over is free | local |
| 7 | The clock's possible small backward jump is not changed yet | A display clock that never goes back | The task says to fix what the run reports; a monotone clock changes what "snaps to every snapshot" means (`02` rule 7), so it needs evidence first | local |
| 8 | The city JSON is written by the watch, not the raw server body | Keeping every answer's text | The store holds mapped snapshots; the mapped city is what the engine ran on, and it is every value a regression fixture needs | local |
