## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | Access token: a JWT signed with HMAC-SHA256 and `Auth:SigningKey` (at least 32 bytes as UTF-8, required in every environment, from user-secrets or the environment), `sub` = the player id (GUID `D`), issuer and audience `citybuilder-api` (constants), lifetime `Auth:TokenLifetimeMinutes` (default 720, 1 to 1440) | An asymmetric key (RS256/ES256); issuer and audience in configuration; a longer default lifetime | One server both issues and checks the tokens, so a shared secret is enough (an asymmetric key matters once another service checks them, M1 accounts); 32 bytes are HS256's key size; a short lifetime limits a leaked token, since M0 has no revocation (`07`, known limitations) | local |
| 2 | The token's lifetime is checked against the server's `TimeProvider` (`LifetimeValidator`), with no clock skew; issuing reads the same clock and floors to the whole second | The handler's own check (machine clock, 5 min skew) | Principle 3: the server clock is the only clock; a fake clock then tests expiry to the second (the last valid second and the first refused one) | local |
| 3 | Only HS256 is accepted (`ValidAlgorithms`), signed tokens required; the handler keeps claim names (`MapInboundClaims = false`), so `sub` stays `sub` | The defaults | Refuses unsigned (`alg: none`) and algorithm-confusion tokens explicitly; the player claim has one name everywhere | local |
| 4 | Endpoints that need a token require it through the `/api/v1` route group (step 2; the dev login opts out); no fallback authorization policy | A fallback policy that requires a token everywhere, with opt-outs for `/health` and OpenAPI | A fallback policy also covers requests that match no endpoint: the dev login path in Production would answer 401 instead of the 404 the spec asks for, and every unknown path would too | project-wide (→ `12` row at finish) |
| 5 | The token tests run over HTTP through a test-only endpoint added by an `IStartupFilter` in front of the server's pipeline (`CurrentPlayerEndpoint`) | Calling the JWT handler directly (`HttpContext.AuthenticateAsync`); a real endpoint such as `GET /api/v1/auth/me` | Tests the real middleware, handler options and `ICurrentPlayer` end to end; a new real endpoint would be a contract change (G-Contract) for a test's sake | local |
| 6 | `Program.cs` reads `AuthOptions` before `app.Run()`, like `DatabaseOptions` | Leaving the validation to `ValidateOnStart` | With the validation inside the host's start, `WebApplicationFactory` sometimes raised `ObjectDisposedException` instead of the validation error (seen once in a parallel run, `Start_TokenLifetimeOutOfRange_FailsValidation`); read before `Run`, the start fails the same way every time (10 runs green) | local |
| 7 | A refused token gets the handler's default 401 (empty body, `WWW-Authenticate: Bearer`) | A ProblemDetails body with `AUTHENTICATION_REQUIRED` now | The error body is the error catalogue's job (M0-34) and is tested with the first game endpoint (M0-28: "unauthenticated → 401 ProblemDetails") | local |
| 8 | `ICurrentPlayer` is an Application port (`Players/`); the Api's `HttpCurrentPlayer` reads the verified `sub` claim through `IHttpContextAccessor` and throws when there is none | Passing `ClaimsPrincipal` to use cases; returning `Guid.Empty` | Use cases stay free of ASP.NET Core (architecture test); an endpoint that forgot to require a token fails loudly instead of acting for nobody | local |
