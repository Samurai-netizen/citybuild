<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | **One PR (owner)** for the whole task, about 2,000 changed lines with tests and docs, above the ~600 lines of `14`; one commit per green step so the PR can be reviewed commit by commit | Split into M0-08a (state, queries, factory) and M0-08b (mutations) | The owner's choice (Owner input); the mutations need the queries, so the spec is one unit | local |
| 2 | Folders and namespaces: `Runtime/State/` is `CityBuilder.Simulation.State` (`CityState`, `Building`, `BuildingPhase`, `ActiveResearch`, `CityFactory`, `CityQueries`); `Runtime/Rules/` is `CityBuilder.Simulation.Rules` (`CityRules`, `MutationResult` and its error codes, step 4), the place recipe "New command" in `19` names | Everything in the root namespace; one `City/` folder | Folder = namespace (M0-07a decision 11); the recipe already names `Rules/` | local |
| 3 | **Canonical form of a building:** the fields a phase doesn't use are 0, and `PhaseEndsAt` is null when idle or frozen. Producing uses `PhaseStartedAt` for the cycle's start (the snapshot in `05` shows it); upgrading sets `TargetLevel = Level + 1`. `BuildingPhase`'s doc lists the fields of each phase | Nullable fields like the columns of `06` (`target_level`, `cycle_labor`, … null) | The spec marks only `PhaseEndsAt` nullable; two buildings in the same situation are equal field by field, which the structural comparisons of M0-14 need; M0-20 maps 0 ↔ NULL (Follow-ups) | local |
| 4 | **State changes in place, only through the engine:** public getters, private setters, and internal transitions (`Building.StartConstruction`, `StartUpgrade`, `AssignWorkers`; `CityState.AddItems`, `RemoveItems`, `AddBuilding`, `StartResearch`); the lists are read-only views (`ReadOnlyDictionary` over a `SortedDictionary`, `List.AsReadOnly`), so a cast can't change them. M0-09 adds the transitions `Advance` needs | An immutable state copied on every change; public setters | `Advance` must be allocation-light (~200k steps); the server and the client can read the state but change it only through `CityRules` and `Advance` (principle 1) | local |
| 5 | **Restoring constructors check what needs no content** and throw `ArgumentException`: `Building` checks ranges and the canonical form of its phase (decision 3), a constructing building has no workers, a producing one labor ≥ 1 and remaining labor within it; `CityState` checks clock ≥ 0, era ≥ 1, next id ≥ 1, no negative or repeated item, unique building ids below the next id, one building per tile, no research completed twice, the running research not completed. Whether a type exists or a level is within its max needs content: a query then throws `InvalidOperationException` ("the city and the content don't belong together") | No checks; a separate validator against the content | Validate at the boundary (`.claude/rules/simulation.md`); a mapping bug in M0-20 fails at load, not as a broken invariant later | local |
| 6 | **Inventory:** no separate `Inventory` class (step 2 of the plan named one): `CityState` holds a `SortedDictionary` in ordinal item order that stores only quantities above 0 (taking the last unit removes the entry; a restore leaves zeros out); `GetQuantity` gives 0 for the rest. **Completed research:** a sorted `List<ResearchId>` with binary search, exposed read-only (netstandard2.1 has no read-only set) | An `Inventory` class (one more type for four small methods); every content item always present; `SortedSet` | One canonical form that doesn't depend on the content's item list; deterministic iteration (`04` §9) | local |
| 7 | **Derived queries** are the static class `CityQueries` with `(city, content, …)` arguments, not members of `CityState`, which holds no content. The spec's `EffectiveCap(item)` is `TryGetEffectiveCap`, like `GameRules.TryGetBaseStorageCap`, because uncapped items have no cap; worker sums are `long` (M0-07a decision 7); `WorkersProvided` sums the level's `WorkersProvided` of every completed building (producers provide 0 by content rule 3); `IsUnlocked` is false for an unknown type; `EffectiveLabor` throws `ArgumentException` for a house or an unknown type | Members of `CityState` with a content argument; a nullable cap | The state stays pure data; the names say what happens with uncapped items | local |
| 8 | Tests: `CityFixture` builds cities and one building per phase (exactly the fields the phase uses) over the synthetic `ContentFixture`; `CityDump` writes every stored value as text, so a test can check that a rejected mutation changed nothing. Theories with a case dictionary keyed by name, as in `ContentShapeTests`. The fixture's content property is `TestContent`, because `Content` clashes with the namespace `CityBuilder.Simulation.Tests.Content` | A copy of the fixture content per test class | `.claude/rules/tests.md` (builders, not copied setup) | local |
| 9 | Steps 2 and 3 are one commit: the state's doc comments point at `CityQueries`, and the build fails on an unresolved reference. Until step 4, `CityRules` is named in `<c>` instead of `<see cref>` | Two commits with a placeholder | Every commit builds | local |
