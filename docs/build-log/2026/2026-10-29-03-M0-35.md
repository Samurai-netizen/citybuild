## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | The fast clock counts from a fixed origin: `now = Origin + (real now − Origin) × scale`, `Origin` = 2026-01-01T00:00:00Z (`ScaledTimeProvider`) | The origin at startup; the Unix epoch | From the startup time, every restart would move the clock back behind every stored city (frozen until it caught up); from the Unix epoch, 56 years × the scale passes the year 9999 above a scale of about 140. A fixed recent origin keeps the clock continuous across restarts with the same scale, and a scale change moves it, which is the documented "reset the dev database" | local |
| 2 | `Simulation:DevTimeScale` is 1 to 1000 | No upper bound; 3600 | 1000 × the real years since the origin must stay below 7973 years (`DateTimeOffset.MaxValue`): safe until about 2033; 60 (the plan's value) until well past 2100. 1000 already plays the 8-hour cap in under 30 s | local |
| 3 | The scaled clock is *the* server `TimeProvider`: settlements, commands, the dev login's new city, repository timestamps and token times all read it | A second clock only for game progress, the tokens on the real one | One clock keeps `serverTimeUtc`, the city clocks, `created_at` and `expiresAtUtc` in one time line; the token tests move token times with the fake clock, as decision 040 wants. Cost: tokens age at the same speed (12 h last 12 min at 60); the client logs in again on expiry (`05`), and the key's row in getting-started says so | local |
| 4 | `rules.timeScale` is read from the registered clock (`ServerClock.TimeScaleOf`: a `ScaledTimeProvider`'s `Scale`, else 1), not from the options | Read `SimulationOptions` and the environment in the endpoint | One source: the value is what the clock does; a test's `FakeTimeProvider` reports 1 | local |
| 5 | Only `GetUtcNow` is scaled; timestamps, elapsed times and timers stay real (the base class) | Scale timestamps too | Durations in the logs are real request times; nothing in the server uses `TimeProvider` timers; the rate limiter has its own clock | local |
| 6 | The start resolves the clock before `AuthOptions` (so the validation fails before `Run`, as for the other options) and logs a fast clock as a warning, event id 7000 (ids 7000–7999 for clock messages) | Only `ValidateOnStart` | Same pattern as the database and auth options (the module doc's Startup section) | local |
| 7 | Correlation is the framework's: with `IncludeScopes` every line of a request already carries the activity scope (`TraceId`, `SpanId`, `ParentId`) and the hosting scope (`RequestPath`, ASP.NET Core's `RequestId`). The answer's `traceId` is the W3C id `00-<TraceId>-<SpanId>-<flags>`, so a player's report finds the lines by its middle part; tested | A middleware with a scope of its own; `ActivityTrackingOptions` set by hand | The host builder already sets `SpanId, TraceId, ParentId` (probe in a test: M0-02's follow-up "not set yet" was outdated); a second scope would only repeat it | local |
| 8 | Our lines name the command's request id `RequestId` (as `.claude/rules/server.md` asks) although the hosting scope has a `RequestId` of its own (the connection's request number, such as `0HNPLQPQGB5G1`); the JSON console keeps them apart (`State.RequestId` vs a scope), and docs/api explains the difference | Name ours `CommandRequestId`; drop the hosting scope | The rule and `05` call it `requestId`; the hosting scope also carries `RequestPath`, which the lines need | local |
| 9 | `PlayerId` is a named value of each of our messages (null when the request has no token), not a scope | A scope middleware after the token check | A named value is in `State`, where the other values of the event are; the framework's own lines don't need it | local |
| 10 | Event ids: 3001 rate-limit hit and 3002 a conflict outside a command (the 3000 block of errors and requests), 4000–4999 authentication (4000 dev login, 4001 dev login refused, 4002 token accepted, 4003 401), 5000–5999 commands, 6000–6999 settlements, 7000–7999 the clock | One block for everything new | Decision 029 gives each feature a block | local (029 lists them, `12`) |
| 11 | Authentication: the dev login logs the player and whether it is new (Information) or the refusal's code (never the display name: personal data, `07`); an accepted token at Debug (every game request has one); a 401 at Warning with the reason `NoToken` or the type name of the validation failure (an expired token is `SecurityTokenInvalidLifetimeException`, from the server-clock lifetime validator), never the failure's message, which can quote the token | Information for accepted tokens; the failure message | Every request would write a line; the message isn't needed to tell the kinds apart | local |
| 12 | A rate-limit hit is a Warning with the class, method, path, player and `Retry-After`; a request counted by address (the dev login) names no player and never the address | Log the partition key | An IP address is personal data (`07` → Logging policy) | local |
| 13 | A body that doesn't bind (400 from `BadHttpRequestException`) writes no line of ours | A line per refused body | The answer says what is wrong, the framework logs it at Debug, and junk bodies would let anyone fill the log | local |
| 14 | Endpoint lines use the endpoint class as the category (`ILoggerFactory.CreateLogger(typeof(AuthEndpoints).FullName)`; the bearer events `BearerChallenge`, the limiter `RateLimits`) | `ILogger<SomeType>` of an Application type | The endpoint classes are static, so they can't be a type argument; the category says where the line was written | local |
| 15 | `CommandResult` carries the `Settlement` of a success or a rejection (null for the outcomes decided before the settle), and `Settlement` has `ClockBehindSeconds`, computed by `CitySettler` | Log in Application; recompute "behind" in the Api from the snapshot | Application has no logging package (M0-23 decision 7, `14`); the engine's window doesn't keep now, and a rejected command has no snapshot. Only the pipeline builds a `CommandResult`, so the new required parameters break no caller | local |
| 16 | Command lines: 5000 accepted, 5001 rejected with the answer's code (a rule's, `INVALID_ARGUMENT`, `IDEMPOTENCY_CONFLICT`), 5002 replayed, all Information; 5003 a concurrency conflict, Warning. `CommandResponses.ErrorOf` gives the answer and the line the same code | One event per code; Warning for rule refusals | A refusal by a rule is normal play; a conflict is what ADR-0009 watches. One mapping can't let the logged code drift from the answered one | local |
| 17 | Settlement line 6000 for every settle (from `GET /city` and from a command that settled), Information: `Trigger` (`city` or the command type), `ElapsedSeconds`, `ProductionSeconds`, `Events` (constructions and upgrades, research, an era, completed), `ResearchCompleted` (ids), `DurationMs`; written before the command's line | Only when something happened; Debug | ADR-0005 watches settle durations and event counts, which needs every settle; a poll every 30 s per player is one line | local |
| 18 | The clock-behind warning is 6001 with `SecondsBehind`, beside the settlement line (closes M0-28 decision 14) | Inside the settlement line | A warning level of its own is what `04` §1 asks for and what an operator filters on | local |
| 19 | `DurationMs` is real time from the start of the endpoint's work (`Stopwatch`), to 0.1 ms (`Http/RequestDuration`) | `TimeProvider` timestamps; the whole request | The fast clock must not change durations; the framework's own request log (Information in `Microsoft.AspNetCore.Hosting`, off by default) gives the whole request | local |
