| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | `MutationResult` gets `Spent` and `Refunded` (item quantities, empty on a rejection and when nothing moved); the mutations fill them | Compute spent and refunded in the tests from the content (cost of the type, upgrade cost, recipe inputs) | The task says "from mutation results"; a copy of the rules' cost logic in the tests would agree with a wrong rule; M0-26 needs the same numbers for `COST_*`/`REFUND_*` ledger rows (`06`). Additive: no API, DB or content change | local (engine API, additive) |
| 2 | One observer runs every invariant over a seed's history at once; each invariant has its own test case per content that reads the cached result (first failure per invariant) | One full replay per invariant and content (10 × 2 runs) | `04` §10 wants a test per invariant, and the stepped replay costs too much to run twenty times | local |
| 3 | Advances within the cap are observed event by event (a zero-length step, then one step to each next due time) | Observe only between the generated operations | Between operations many cycles start and finish unseen; event steps make every start and completion visible, so invariants 8 and 11 can be checked exactly. Split invariance (property 2) makes the stepped city equal to the generated one, and the observer asserts that | local |
| 4 | City copies for the observer come from the public restore constructors (`CityState`, `Building`), in test code | Replay the history again for every copy (M0-14 decision 7) | A copy before every step must be cheap; the restore constructors are public and validate the values | local |
| 5 | An advance beyond the cap runs whole on the city; a copy is stepped to the cap, then a test model of the dormant tail finishes it (timers complete in time and id order, cycles deliver, construction auto-staffs, nothing starts), and the result must equal the whole advance | Step the tail too (a split beyond the cap reopens production, so it changes the result); only check `PhaseStartedAt ≤ T0 + cap` at the end | The tail cannot be split, and a check of the end state misses cycles that start and finish inside the tail; the model is small because nothing starts there | local |
| 6 | The result lists are the content's own read-only lists (cost lines as listed, a line may be 0); `Applied` is internal | Copy into new lists; drop zero lines; a public factory | No allocation and nothing to keep in sync; only the engine knows what moved, as `ItemQuantity`'s constructor is internal too | local |
| 7 | Branches: after 5 % of the history's steps, a copy takes a random command (80 %: a worker change or an upgrade on a producing building, the upgrade preferably where the cycle took inputs; else `CityGenerator.RandomCommand`) and a stepped advance of 0–600 s, checked with a fork of the checks; a rejected branch command is skipped | Change the generator's mix (aim upgrades at running cycles) | The generator's histories stay as M0-14 made them (its floors and properties unchanged); commands now land at any second, mid-cycle included, which is what the task means by interleaving mutations | local |
| 8 | The coverage test writes every count to the test output and asserts floors: ≥ 1000 spending steps, ≥ 100 refunding steps, a negative advance per seed | Only assert | The numbers go into this log and show how much each check really saw | local |
| 9 | Floors are about a tenth or less of today's counts on the smaller content, round numbers | Floors near today's counts | A generator or observer change that stops reaching a case fails; normal changes to the content or generator don't | local |
| 10 | Invariant 11 is a separate stateful `LaborLedger` (forked with the checks for branches); it identifies a cycle by its building and `PhaseStartedAt` | Check the engine's `LaborRemaining` and `PhaseEndsAt` against each other | Checking the engine's fields against each other would agree with a wrong segment update; the ledger counts worker-seconds itself, which is what the invariant says | local |
| 11 | The checks' power was shown by planting engine bugs with a throwaway script in the scratchpad and recording the results here, as in M0-14 (decision 18 there) | Committed "mutant" tests | The engine must not carry test hooks | local |

## Problems and surprises
- The generated histories almost never upgrade a building mid-cycle (refunds: 1 step on golden-v1, 0 on the fixture), so conservation's
  refund term was barely tested; branches fixed it (decision 7).
- A planted "negative stock" bug can't reach invariant 5: `ItemTotals.Set` throws first. The engine guards stock three times (the rule's
  check, `RemoveItems`, `ItemTotals`); invariant 5 is the outermost.
- About 1250 changed lines of C#, nearly all test code (the engine change is about 50); `14` suggests about 600. The task asks for ten
  invariants and the observer they share.
