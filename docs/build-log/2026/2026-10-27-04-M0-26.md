## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | A command is a type that implements `ICityCommand`, and the pipeline is the only thing that runs it. A command never sees the transaction: it gets only `CityState` and `GameContent` and returns the engine's `MutationResult`. An architecture test allows only `SettleCity` and `CommandPipeline` to hold `ICityTransactionRunner` | A base handler class that each command overrides; each command calling the runner itself | No command can write, skip the receipt or lock anything: the rule is in the types, and the test catches a new holder | local |
| 2 | The response is a JSON string end to end. The pipeline gets a function from the caller (the endpoint, M0-29) that turns the success (request id, city, settlement, new state version, server time) into the response JSON. It stores that string in the receipt and returns it; a replay returns the stored string | An Application snapshot model serialized by the pipeline; a port `ICommandResponseWriter` | The snapshot DTO belongs to the Api (M0-28), and a replay must return the response as it was then (ADR-0004), not one rebuilt from today's content. A delegate needs no port without an implementation until M0-29 | local |
| 3 | The owner's choice (2026-10-27): `command_receipts.response_json` becomes `json` (a new migration), so a replay returns the stored text byte for byte | Keep `jsonb`: PostgreSQL then reorders object keys and rewrites whitespace, so a replay is the same JSON value but not the same bytes, and M0-27 compares parsed JSON | Byte-identical replays are the simplest guarantee to test and to reason about; nothing queries inside receipts, so `jsonb`'s indexing is unused. A schema change (`06`), hence the owner's choice | project-wide (→ `12` row) |
| 4 | The canonical payload is the command's JSON (System.Text.Json, part of .NET) with its data properties ordered by ordinal name, prefixed by the command type; the hash is SHA-256 of its UTF-8 bytes. The members of `ICityCommand` other than the request id are left out | Declaration order; `[JsonPropertyOrder]` on every property; a hand-written payload per command | The order can't change by reordering code, and no command can forget an attribute. The type in the hash makes the same request id on another command a conflict. A pinned hash value in a test catches any change to the format | project-wide (→ `12` row) |
| 5 | The receipt lookup runs after the runner has locked and loaded the city (it loads everything before the work runs) | Looking up the receipt before loading the child rows, as `06`'s sketch shows | Keeps `ICityTransactionRunner` unchanged. A replay is rare, so the extra load costs little. The order that matters (lock, then lookup, then settle) holds | local |
| 6 | A replay or a conflict returns before the settle and writes nothing, so the runner commits an empty transaction. That has the same effect as a rollback | Adding a rollback option to the runner | Nothing is staged then, so a commit and a rollback leave the same database; the runner stays one code path | local |
| 7 | The command's ledger rows (`ref_type` `command`, `ref_id` = request id) go between the settlement's advance and the closing advance: settlement rows, then refund rows, then cost rows (per item, ordinal), then the closing advance's rows (`SETTLEMENT_*`, the settlement's reference). A settle without a command keeps its rows as now (one per item and direction) | All settlement rows first, then the command's | Each `balance_after` must follow what happened. An upgrade's refund can be consumed by a cycle that the closing advance starts, so putting the settlement rows first could take a balance below 0 | project-wide (`06` text) |
| 8 | A successful command always saves the city with its receipt (`state_version` + 1), even when the mutation changed nothing (the same worker count) | Saving only on a change | The receipt must be stored for every successful command, and a receipt describes a saved state | local |
| 9 | The shape check is the command's own (`ValidateShape`: null when fine, or a detail), plus the pipeline's own check of an empty request id. It runs before the transaction and returns `INVALID_ARGUMENT` without touching the database | Checking the shape in the endpoint only | The spec puts it first in the pipeline. JSON binding errors stay with the Api and the error catalogue (M0-34) | local |
| 12 | The receipt race test of the fakes uses `BeforeNextWrite` (another request commits between this one's lookup and its write) and a fake unique key on receipts, not an exception thrown by hand | `FailNextWrite = new DuplicateKeyException()` plus a receipt stored up front | A receipt stored up front would be found by the lookup under the lock, so the race path would never run; the hook reproduces the real timing | local |
| 13 | `PersistenceModelTests` now expects `response_json` as `json` | Leaving the test at `jsonb` | It pins the schema of `06`, which the owner changed (decision 3); the assertion is as strict as before | local |
| 14 | `CommandPipeline` is registered (scoped) in `Program.cs` now, although its first endpoint is M0-29 | Registering it with the first endpoint | M0-27's integration tests resolve it from the real host before M0-29; one line, no endpoint, no contract change | local |
| 10 | The pipeline returns a result (succeeded, replayed, rejected with a `MutationErrorCode`, invalid argument, idempotency conflict). `ConcurrencyConflictException` still propagates; its ProblemDetails mapping is M0-34 | Exceptions for rejections | `14`: business-rule failures are results | local |
| 11 | The shared steps are an internal class, `CitySettler`, used in a fixed order (begin → record a command → close → changed / ledger); the running balances are `LedgerWriter`'s, which `Settlement.LedgerEntries` uses too. The stock check runs before the rows are built and now includes the command's lines | A static helper with many parameters; keeping the steps copied in `SettleCity` and the pipeline | One copy of the settle for the settle and every command; the class checks the order (a second record or close throws); checking first keeps an engine bug an `InvalidOperationException` | local |
