### Session 1 — 2026-10-27 · Claude Code / claude-opus-5-5
- **Start:** PR #37 (M0-25) is merged (`48c7f84`), so the branch starts from `main`; M0-25's board row goes to `Done` with this task. The
  owner first asked for M0-27, which depends on this task; it was not started (its precondition failed), and the owner then started M0-26.
- **Plan** (`[PLAN]`: waits for the owner's approval before any code):
  1. **Shared settle steps:** move the settle's steps out of `SettleCity` into one internal piece that both the settle and the pipeline
     use: the window and the advance, `MarkSettled`, the closing zero-length advance, the change check, the stock check (now with a
     command's cost and refund) and the ledger rows in the order things happened. `SettleCity` behaves exactly as before; its tests stay
     unchanged and green.
  2. **Command contract:** `Application/Commands/`: `ICityCommand` (request id, command type, shape check, the mutation through `CityRules`
     on the city state and content only, the ledger reasons of its cost and refund), the canonical payload and its SHA-256 hash, the
     pipeline's result type, and the `ICommandReceiptRepository` port (find a receipt by `(playerId, requestId)`). Tests: the hash is
     fixed for a known command (a pinned hex value), independent of property declaration order, and different for another command type or
     another value.
  3. **`CommandPipeline`:** shape check → `ICityTransactionRunner` → receipt lookup (same hash → stored response, nothing written;
     different hash → `IDEMPOTENCY_CONFLICT`, nothing written) → settle → mutation → on a rule error: closing advance, save the settlement
     only if it changed, return the code, no receipt → closing advance → save city + ledger (settlement, `COST_*`, `REFUND_*`) + receipt →
     the response. A `DuplicateKeyException` on the save → (rolled back) read the stored receipt: same hash → its response, different hash →
     conflict, none → rethrow. Application tests with fakes for the order (event list) and every branch; architecture test: only `SettleCity`
     and `CommandPipeline` hold `ICityTransactionRunner`.
  4. **Infrastructure:** `CommandReceiptRepository` (a no-tracking read by key), registered with the other ports; the column change of
     decision 3 if the owner picks it (a new migration). Database tests: found, not found, another player's request id not found, the
     stored response read back as written.
  5. **Docs and finish:** the Docs impact rows, decision row(s) in `12`, `CHANGELOG`; Definition of Done, line-by-line self-review, PR.
- **Done:** start (branch, this entry, resume point, board).

## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | *Proposed:* a command is a type that implements `ICityCommand`, and the pipeline is the only thing that runs it. A command never sees the transaction: it gets only `CityState` and `GameContent` and returns the engine's `MutationResult`. An architecture test allows only `SettleCity` and `CommandPipeline` to hold `ICityTransactionRunner` | A base handler class that each command overrides; each command calling the runner itself | No command can write, skip the receipt or lock anything: the rule is in the types, and the test catches a new holder | local |
| 2 | *Proposed:* the response is a JSON string end to end. The pipeline gets a function from the caller (the endpoint, M0-29) that turns the success (request id, city, settlement, new state version, server time) into the response JSON. It stores that string in the receipt and returns it; a replay returns the stored string | An Application snapshot model serialized by the pipeline; a port `ICommandResponseWriter` | The snapshot DTO belongs to the Api (M0-28), and a replay must return the response as it was then (ADR-0004), not one rebuilt from today's content. A delegate needs no port without an implementation until M0-29 | local |
| 3 | *Proposed, owner's choice:* `command_receipts.response_json` becomes `json` (a new migration), so a replay returns the stored text byte for byte | Keep `jsonb`: PostgreSQL then reorders object keys and rewrites whitespace, so a replay is the same JSON value but not the same bytes, and M0-27 compares parsed JSON | Byte-identical replays are the simplest guarantee to test and to reason about; nothing queries inside receipts, so `jsonb`'s indexing is unused. A schema change (`06`), hence the owner's choice | project-wide (→ `12` row) |
| 4 | *Proposed:* the canonical payload is the command's JSON (System.Text.Json, part of .NET) with its data properties ordered by ordinal name, prefixed by the command type; the hash is SHA-256 of its UTF-8 bytes. The members of `ICityCommand` other than the request id are left out | Declaration order; `[JsonPropertyOrder]` on every property; a hand-written payload per command | The order can't change by reordering code, and no command can forget an attribute. The type in the hash makes the same request id on another command a conflict. A pinned hash value in a test catches any change to the format | project-wide (→ `12` row) |
| 5 | *Proposed:* the receipt lookup runs after the runner has locked and loaded the city (it loads everything before the work runs) | Looking up the receipt before loading the child rows, as `06`'s sketch shows | Keeps `ICityTransactionRunner` unchanged. A replay is rare, so the extra load costs little. The order that matters (lock, then lookup, then settle) holds | local |
| 6 | *Proposed:* a replay or a conflict returns before the settle and writes nothing, so the runner commits an empty transaction. That has the same effect as a rollback | Adding a rollback option to the runner | Nothing is staged then, so a commit and a rollback leave the same database; the runner stays one code path | local |
| 7 | *Proposed:* the command's ledger rows (`ref_type` `command`, `ref_id` = request id) go between the settlement's advance and the closing advance: settlement rows, then refund rows, then cost rows (per item, ordinal), then the closing advance's rows (`SETTLEMENT_*`, the settlement's reference). A settle without a command keeps its rows as now (one per item and direction) | All settlement rows first, then the command's | Each `balance_after` must follow what happened. An upgrade's refund can be consumed by a cycle that the closing advance starts, so putting the settlement rows first could take a balance below 0 | project-wide (`06` text) |
| 8 | *Proposed:* a successful command always saves the city with its receipt (`state_version` + 1), even when the mutation changed nothing (the same worker count) | Saving only on a change | The receipt must be stored for every successful command, and a receipt describes a saved state | local |
| 9 | *Proposed:* the shape check is the command's own (`ValidateShape`: null when fine, or a detail), plus the pipeline's own check of an empty request id. It runs before the transaction and returns `INVALID_ARGUMENT` without touching the database | Checking the shape in the endpoint only | The spec puts it first in the pipeline. JSON binding errors stay with the Api and the error catalogue (M0-34) | local |
| 10 | *Proposed:* the pipeline returns a result (succeeded, replayed, rejected with a `MutationErrorCode`, invalid argument, idempotency conflict). `ConcurrencyConflictException` still propagates; its ProblemDetails mapping is M0-34 | Exceptions for rejections | `14`: business-rule failures are results | local |
