- **Plan** (tests only; no production code expected):
  1. **Helpers:** `IntegrationTests/Commands/`: a test command that places a building through `CityRules.PlaceBuilding` (PlaceBuilding is
     M0-29), a response writer that writes the success as JSON, and a helper that runs `CommandPipeline` as one request (its own scope).
  2. **Sequential idempotency** (`CommandPipelineDatabaseTests`): a retry returns the identical response text and adds no ledger rows,
     no receipt and no version (also after the clock moved on: a replay doesn't settle); a retry on a new host on the same database (host
     restart); same `requestId` + another payload, and + another command type → `IdempotencyConflict`, nothing written; another player's
     `requestId` never matches (same and other payload: each runs as new on their own city).
  3. **Concurrency and the receipt race:** 10 identical requests queued behind the city's held lock (`DatabaseLocks`, waiting confirmed in
     `pg_stat_activity`) → one `Succeeded`, nine `Replayed`, one text, one building, one receipt, one set of cost rows, version + 1; the
     unique-violation path on PostgreSQL: a receipt of the same key inserted by a transaction of the test's own, committed while the
     command waits on the unique index → the command rolls back whole (its settlement too) and answers from that receipt.
  4. **Rejection:** a business-rule rejection (occupied tile) after time passed commits the settlement (new clock, `SETTLEMENT_*` rows,
     version + 1) and stores no receipt and no cost rows; the same request again after more time is not a replay, it runs and is
     rejected again.
  5. **Docs and finish:** Docs impact rows, Definition of Done, line-by-line self-review, PR.
