## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | The board row of M0-52 is set to `Done` in the start commit | Leaving it `In review` | PR #72 is merged (the owner merged it); the next task closes the row | local |
| 2 | The report is made from every snapshot the store takes (startup, poll, command answer), not only from `GET /city` answers: `elapsedSeconds ≥ 300` can only come from real time away, so a routine poll (about 120 s) never qualifies | Only the startup and the poll-on-resume answers | The command that wakes the app up after hours is settled first and answers with the long settlement; a flow tied to one request kind would lose it | local |
| 3 | `CitySnapshot.Settlement` is an optional constructor argument (null = unknown), not a required one | Requiring it | Five existing call sites (tests, `EmptySnapshot`) build snapshots without an answer; null says "no settlement known" and the report shows nothing for it | local |
| 4 | `SettlementSummary` refuses a negative number and production time above the elapsed time; the mapper reports that as `CLIENT_INVALID_RESPONSE` | Trusting the server | Same rule as the city: the client holds nothing its engine could not; the server's `min(elapsed, cap)` makes it impossible in a real answer | local |
| 5 | The duration reads `7 h 12 m` (spaces, hours and minutes, seconds dropped, under a minute `30 s`), not `DurationText`'s `7h 12m` | Reusing `DurationText` | The task's own example writes `7 h 12 m` and `8 h`; a card's `1h 5m 10s` is built for short spans | local |
| 6 | The same sentence for several buildings is one line with a count (`Cottage built ×3`); a level 1 completion is `built`, level 2 or more `upgraded to level N` | One line per building; reading the phase | The city of the snapshot already says the level reached, also when the next upgrade has started; a long absence completes many cottages | local |
| 7 | The effect words moved from `ResearchNodeModel` to a public static `ResearchEffectText`; the research screen's output is unchanged | Copying the code into the report | One wording of a research effect on both screens (removes real duplication, `02` 13) | local |
| 8 | A long absence in which nothing happened is still reported (title, `Nothing was produced or finished.`); a settlement under 300 s never is | Hiding an empty report | The player was away for the stated time; telling them nothing changed is information, and the panel is dismissable | local |
| 9 | The panel is modal: a full-screen scrim takes the pointer, sorting order 2.5 (over the placement bar at 2, under the toasts at 3), and only Continue closes it (a tap on the scrim does not) | A non-modal card beside the menus; a tap on the scrim dismisses | The report is read once and a stray tap on the ground must not lose it; the toasts still show a command's result over it | local |
| 10 | The panel joins the `MenuGroup` with `Dismiss` as its close action, and joins before the flow is made | The flow's own `Close`; joining after the flow | The flow shows the startup report in its constructor, so the group must already know the panel to close the other menus; `Dismiss` is safe when closed (OD-16) | local |
| 11 | A newer report arriving while one is open replaces its words (no second `Opened`) | Merging the two reports | Two long settlements in a row need a connection that failed for minutes; the newest numbers are the ones since the last settlement. A merge is not in the task | local |
| 12 | The flow looks at the snapshot the store already holds when it is created | Waiting for the next `SnapshotChanged` | `StartupFlow` stores the first `GET /city` before `GameRoot` builds any view, and that is exactly the answer after a long absence | local |
