## Problems and surprises
- Doc comments are not inert in `CityBuilder.Api`: the OpenAPI package (`Microsoft.AspNetCore.OpenApi`, .NET 10) compiles them into the
  assembly to describe endpoints and schemas, so the acceptance criterion "the server assemblies compile byte-identical" holds for four
  of the five; for Api the difference is explained above and the served OpenAPI document is unchanged.
- Step 7 wrote its comment lines into protected files (`scripts/dev/*`, `.claude/hooks/*`, `.github/workflows/*`) with a session script
  run through Bash, so the `ask` prompt that `.claude/settings.json` shows for an edit of a protected file never appeared. The edits are
  comment lines that the approved CR asks for (and the new `check-docs.sh` section, written with the Edit tool), but the prompt is the
  owner's chance to see each edit, so this is reported to the owner. From step 8 on, protected files are edited with the Edit tool only.
- The session script that inserted the step 7 comments read and wrote text with Python's default newline handling, so it turned
  `scripts/dev/test-unity.ps1` (CRLF by `.gitattributes`) into LF in the working copy; git stores LF either way, so the diff was only the
  three comment lines. The file was converted back to CRLF before the commit.
- `CityGenerator.PlaceBuilding` said "Half the time a type the city doesn't have yet", but the code has chosen one with a 75 % chance
  (`random.Chance(75)`) since M0-14. The comment now says three times in four; the code is unchanged (this CR changes no behaviour).

## Follow-ups
- Found while reviewing, not changed (a content rule is behaviour): content may hold quantities and windows up to 10^12, and no rule
  bounds an effective cap or the total of an uncapped item, so absurd content could overflow a `checked` sum and make a settlement or
  `ProductionDisplay.SecondsUntilFull` throw. Real content is many orders of magnitude below; a content rule that bounds
  `quantity × cycles per window` (and caps with their bonuses) would close it.
