## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | The store holds a Core type `CitySnapshot` (version, content version, the city in the engine's terms); `SnapshotMapper` in Net builds it from the DTO | keep the DTO in the store (Core cannot name it: `03`, `09`); put the store in Net (`09` places it in Core) | The dependency direction is fixed; the mapper sits where `ContentMapper` already does | local |
| 2 | "Immutable" is real: the snapshot's `CityState` is private and only `CopyCity()` leaves it. The engine's `CityState` itself stays mutable | expose the state and rely on a comment; add a read-only view or a copy method to the engine | `Simulator.Advance` changes a city in place, so handing out the state could corrupt it. No engine change is needed: every field has a public getter and constructor | local |
| 3 | The mapper sets `TargetLevel` to level + 1 while upgrading and `NextBuildingId` to the highest id + 1: the snapshot holds neither | add them to the snapshot (an API change, G-Contract) | Prediction never places a building, and an upgrade always targets the next level (`Building` requires it). The engine's constructors check everything else: an impossible snapshot is `CLIENT_INVALID_RESPONSE` | local |
| 4 | The store takes a snapshot when `(stateVersion, clock)` is strictly greater. Beyond the spec's "lower `stateVersion` is ignored", it also ignores the same version with the same or an earlier clock | take every equal version | Same version and clock is the same city (`05`: the version rises when a request changes the city), for example a late replay. Taking it would restart the receive time and move the display clock back. The same version with a later clock is still taken | local |
| 5 | Each prediction starts again from the snapshot, not from the last prediction | advance the last prediction by one second | The task requires an exact match with one `Advance` of N. The 8-hour production cap counts from the start of the advance, so steps would give a different city past it. Cost: at most one advance per second, ~37 ms worst case for 8 hours (M0-16), and polling every 120 s (M0-41) keeps N small | local |
| 6 | The store takes the real-time clock as a `Func<double>`; the default constructor reads `Time.realtimeSinceStartupAsDouble` | read `Time` directly | EditMode tests need to control the seconds, and the Unity call stays in one place | local |
| 7 | `SnapshotMapper.Apply(store, ApiResult)` is the one way from an answer to the store: a failure returns the error and leaves the store alone. M0-40 and M0-41 use it too | each caller checks and maps | The task's "rejected command leaves the store unchanged" is tested on this path with the real client and a real 409 fixture | local |
| 8 | `timeScale` travels in `ContentLoadResult` and `StartupOutcome`, not in `GameContent`. `ContentService` treats a value below 1 as `CLIENT_INVALID_RESPONSE` | add it to the engine's `GameRules`; let `DisplayClock`'s check throw at start | It is the server clock's speed, not content (M0-38 left it out on purpose). The factory doesn't see it, so the service checks it, and a bad value is a reported failure rather than an exception | local |
| 9 | When the engine refuses the city (`InvalidOperationException`), `DisplayCity` logs one error, shows the snapshot unadvanced and doesn't try again until the next snapshot | let it throw out of `Update`; retry every second | A display must not take the game down or flood the log. Content that changed on the server is the likely cause, and M0-58 refetches it | local |
| 10 | `CitySnapshot` carries no settlement block; M0-53 adds it when the welcome-back report needs it | map it now | Nothing reads it yet (`02` rule 12) | local |
| 11 | `GameRoot.Update` calls `DisplayCity.Refresh()` although no view reads it yet; the status label stays as it is | wait for the HUD (M0-45) | The M0-38 follow-up asks for the store to take the first snapshot, and this runs the wiring in the real scene. An unchanged second costs a clock read and allocates nothing | local |

## Problems and surprises
- The spec says `rules.timeScale`, but `GameContent` leaves it out on purpose (M0-38), so it had to travel beside the content (decision 8).
- My first engine-refusal test used an idle building of an unknown type: the engine doesn't look at it, so nothing was refused. The test now uses one that completes; the code did not change.
