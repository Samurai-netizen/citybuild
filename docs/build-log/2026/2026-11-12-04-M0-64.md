## Sessions

### Session 1 — 2026-11-13 · Claude Code / claude-opus-5-5
- **Plan** (each step ends green and is checkpointed; no agents):
  1. **Application: `LedgerAuditor`** (`Application/Audit/`) with the read-only port `ILedgerAuditSource` (every city id; one city with
     its ledger rows in id order). Per city: the first row is `STARTING_GRANT`; per item, each `balance_after` runs on from the one
     before (from 0); the sum of the deltas equals the city total (`CityQueries.Totals`: stores, loads, purse). Report every
     mismatch, throw on none. Unit tests in `CityBuilder.Application.Tests` with an in-memory source (clean city, each kind of mismatch).
  2. **Infrastructure: `LedgerAuditSource`** over EF: one repeatable-read transaction per city, no row lock and no settle (the audit
     reads, never writes). The row loading of `CityRepository.LoadForUpdateAsync` moves into one helper both use. Registered in DI.
  3. **Integration test** (`CityBuilder.IntegrationTests/Audit/`, PostgreSQL over HTTP, `FakeTimeProvider`): several players, a long
     seeded random sequence of commands and settles (`GET /city`) with clock jumps, then `LedgerAuditor` over every city: zero mismatches.
     Also a test that the auditor finds a planted mismatch on the real database.
  4. **Docs:** module docs, `docs/testing/README.md`, `docs/how-to/add-command.md`, `CHANGELOG`; then `/finish-task`.

| 1 | M0-63 board row set to `Done` in the start commit; tasks done 67 / 88 | Leave it | PR #91 is merged (`16` §B) | local |
| 2 | The audit reads the city **as stored**: no settle, no lock for update, no write; city and ledger from one snapshot (the source's job) | Settle first, then compare | The ledger describes the stored state; a settle would write rows and change what is audited. Read-only also lets it run against a live database | local |
| 3 | Three checks per city: the first row is `STARTING_GRANT`; each `balance_after` runs on from the row before (from 0); each item's delta sum equals its city total (`CityQueries.Totals`). Items in the ledger but not in the content count against 0 | The sum check only (the spec's words) | The sum alone misses a row written with a wrong `balance_after` or a ledger that never got its grant; both checks are a few lines over the same rows | local |
| 4 | The port gives raw rows (`AuditedLedgerRow`, reason `null` for a reason the server never writes, such as `DEV_ADJUST`), not `LedgerEntry` | Map to `LedgerEntry` | `LedgerEntry` throws on a bad row; an audit must report it. `DEV_ADJUST` rows (server panel, CR-0006) are real changes, so their deltas count | local |
| 5 | `LedgerAuditor.Audit(AuditedCity, GameContent)` is a public static pure function; `AuditAllAsync` and `AuditCityAsync` read through the port. The fixture's sawmill state is extracted as `SettleFixture.SawmillState()` for reuse | Only the async entry points | The pure function is testable without a fake source, and the integration test can audit a city it changed by hand | local |
| 6 | The row loading of `CityRepository.LoadForUpdateAsync` moved into `CityRowsLoader` (tracked or not), shared with `LedgerAuditSource` | A second copy of the twelve queries | One place for "every table of a city"; a new city table is added once | local |
| 7 | `LedgerAuditSource`: one `REPEATABLE READ` transaction per city, untracked, rolled back; `LedgerMapping.ReasonOf` maps the stored text back (null for `DEV_ADJUST`) | `FOR SHARE` lock; no transaction | A snapshot gives city and ledger as of one moment without blocking a player's write; a writer commits both together | local |
| 8 | Run through the integration tests only: `LedgerAuditor` is registered scoped in the Api (no endpoint) and the tests resolve it; no CLI in `tools/` | A tiny CLI (the spec allows either) | A test runs in CI on every PR with no new project, settings or connection handling; a CLI can come later over the same registrations | local |
| 9 | The random game sends all twelve commands, not only the spec's four | The four M0 commands | Plan §0.00: the audits cover the game with CR-0008; roads write `COST_ROAD`, trips and couriers move goods between stores and loads, which every total must survive | local |
| 10 | `RandomHttpPlayer`: a fixed opening (house, woodcutter, scriptorium, research, sawmill, trading post, courier station with a route; each step retried up to 8 times), then weighted random commands drawn from the last snapshot; a settle one step in five; the clock moves 0 to 90 s per step and 1 to 6 h one step in 40. A refusal with a rule's error code is play; a 5xx, a 4xx without a code, `AUTHENTICATION_REQUIRED` after a fresh login, `RATE_LIMITED` or `CONCURRENCY_CONFLICT` fails with seed and step. The test also requires every command to succeed once and eight ledger reasons to appear | Uniform random play | Uniform play spent the purse on roads and never reached trips or upgrades (Problems). The two refund reasons are not required: an upgrade must land on a running cycle; `UpgradeBuildingDatabaseTests` and `SettleCityTripTests` cover them | local |
| 11 | A 401 makes the player log in again and resend the same request | A longer token lifetime in tests | The fake clock jumps hours, past the token lifetime; the real client does the same, and a refused token never reached the command | local |
