## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | Where the mapping lives: DTOs and mappers in `Api/Contracts/`, endpoints in `Api/Endpoints/` (`ContentEndpoints`, `CityEndpoints`); no new Application type for the response | A read model in Application that the Api serializes as is | The recipes put DTOs in `Api/Contracts/`; the engine already holds every derived number (`CityQueries`, `StallReason`), so the mapper only renames and orders; M0-29 reuses the snapshot mapper on `CommandSuccess` | local |
| 2 | `GET /city` has no command, so its snapshot's `requestId` is `null` (the property is always there) | Omit the property; a server-made id | One snapshot type for the city and the commands (the client has one DTO, M0-37); a made-up id would look like a receipt key | local (05 says so) |
| 3 | `rules.timeScale` is the constant 1 until M0-35 builds `DevTimeScale` | Read `Simulation:DevTimeScale` now | M0-35 owns the setting, its guard and the scaled clock; this task only fixes the field's place in the contract | local |
| 4 | Contract tests read the raw JSON text (`JsonShape`: exact property names, JSON types, allowed nulls, per object) and the numbers are checked against frozen content written in the test (`ContentGoldenTests`), with items, buildings, research and cost keys out of order in the file | Deserialize into the DTOs and compare; take the numbers from `mvp-content.json` | A deserialized object can't see a renamed, missing, extra or omitted-null property; the real content changes with balance, a frozen file doesn't (`tests.md`: golden scenarios use frozen content) | local |
| 5 | The wire names of the closed sets are written in the mapper's `switch`es: building kind `House` / `Producer`, effect type `unlockBuilding` / `laborReduction` / `storageCapBonus` (the content file's names); an unknown kind or type throws | `kind.ToString()`; a global `JsonStringEnumConverter` and engine enums in the DTOs | The contract can't change when an engine enum member is renamed; the DTOs stay plain records; kinds follow `phase` (`Producing`, `05`) in PascalCase | local |
| 6 | Level 1's `upgradeCost` and `upgradeSeconds` are `null` | `{}` and 0 | Level 1 is built, not upgraded to; an empty cost and 0 seconds would read as a free instant upgrade (the engine stores them as empty and 0) | local |
| 7 | An effect is one flat record: `type` plus `building`, `item`, `permille`, `amount`, the ones that type doesn't use `null` | Polymorphic JSON with a type discriminator and one record per type | Same shape as the content file; one DTO type for clients (M0-37) whatever JSON library they use; the OpenAPI document stays simple | local |
| 8 | The DTOs are flat `Content*` records in `CityBuilder.Api.Contracts`, not a `Contracts.Content` sub-namespace; no `maxLevel` (the number of levels says it) and no `startingCity` (the city comes from `GET /city`) | A sub-namespace/folder; copying the whole content file | `CityBuilder.Api.Content` (the options) already exists and would be hidden inside `Contracts`; nothing in the task asks for the other fields | local |
