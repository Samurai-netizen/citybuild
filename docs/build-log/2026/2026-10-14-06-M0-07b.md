## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | The loader's tests live in `CityBuilder.IntegrationTests` (fast suite, no `Integration` category, no Docker), next to the startup tests | A new `CityBuilder.Infrastructure.Tests` project | `03` lists four test projects, and the Infrastructure module doc already names this one as its test home; a new project is a layout change outside the task | local |
| 2 | The options class for `Content:FilePath` lives in Api, which resolves the path and hands it to the Infrastructure loader; Infrastructure takes a plain path | Options in Infrastructure | Infrastructure then needs `Microsoft.Extensions.Options`, a package that is not on the approved list as such (`14`); the composition root is where configuration is read | local |
| 3 | Names: `CityBuilder.Application.Content.IContentProvider` (one property, `GameContent Content`); in Infrastructure `Content/`: `ContentFileLoader.Load(path)` (static, pure apart from reading the file), `ContentLoadException`, `ContentProvider` (holds the loaded content, registered as a singleton) | `IContentProvider` in the root namespace or a `Ports/` folder; a provider that loads lazily | A folder per feature, like `Commands/<Name>/` in `19`; a provider that only holds content can't fail after startup | local |
| 4 | The reader is strict: camelCase names, case-sensitive (`PropertyNameCaseInsensitive = false`), `UnmappedMemberHandling.Disallow`, `AllowDuplicateProperties = false`, `JsonNumberHandling.Strict` (no numbers in strings); the options are made read-only once. A JSON problem (unreadable file, syntax, wrong type, unknown field, repeated key, top-level `null`) is **one** error, System.Text.Json's message with its JSON path and line, because the parser stops there; rule and shape problems are **every** error of the factory | Lenient web defaults; collecting several JSON problems by hand | Decision 8 of M0-07a; a misspelt field would otherwise be dropped and then reported as "missing", far from the typo | local |
| 5 | Every load failure is one exception type, `ContentLoadException`: `FilePath`, `Errors` (one line each; rule errors as `ContentError.ToString()`: code, path, message) and a message that names the file and lists every error on its own line | Return a result object; reuse `InvalidDataException` | Startup must stop, and the host prints an unhandled exception's message, so the message is the report; tests can still check the list | local |
| 6 | `server/content/*.json` is copied by the Api project (`None` item, `CopyToOutputDirectory` and `CopyToPublishDirectory`) to `content/` in its output; projects that reference Api get the copy too, so the tests load the very file the server loads (`ContentFiles.RealMvpContentPath`). The real-file test asserts only that it loads, with no game numbers (`24` → Ownership of numbers) | A test that reads `server/content/` through a path relative to the repository | One path for server and tests; a content edit reaches both on the next build | local |
| 7 | Loader tests write each broken file from the real content with one change (`JsonNode`), in a temporary directory per test that is deleted afterwards (`ContentFileDirectory`). They match on error codes and paths built from the ids in the file, never on game numbers; a repeated key is written through a text marker, because System.Text.Json never writes one | A hand-written broken file per case; the engine's `ContentFixture` (another test project, and C# objects, not JSON) | The JSON layer is what these tests are about, so they need real JSON; one change per case, like M0-07a decision 16 | local |
| 8 | `ApplicationDependencyTests` and `InfrastructureDependencyTests` now take the assembly from `typeof(IContentProvider)` and `typeof(ContentFileLoader)` instead of loading it by name; the comment about the placeholder is replaced, the assertions stay | Leave them for M0-19/M0-65 | The M0-06 and M0-07a follow-ups asked for it once the first type exists; a test bound to a type inspects the built assembly | local |
| 9 | **Startup:** `ContentOptions` (section `Content`) bound, validated (`FilePath` not blank) and `ValidateOnStart`; `IContentProvider` is a singleton built by a factory that runs the loader; `Program.cs` resolves it right after `Build()`, before any endpoint is mapped and before `Run()`. A blank key (`OptionsValidationException`) or bad content (`ContentLoadException`) is an unhandled exception there: the process stops with a non-zero exit code and the runtime prints the message, every error on its own line, to stderr | An `IHostedService` that loads in `StartAsync`; catching the exception and logging it as JSON before `Environment.Exit(1)` | The simplest place that runs before requests; the same behaviour as any other failed options validation; tests see the exception from `WebApplicationFactory.Services` | local |
| 10 | The default `Content:FilePath` (`content/mvp-content.json`) is in `appsettings.json`, so every environment has it; a relative path is resolved against the app's base directory (`Path.GetFullPath(path, AppContext.BaseDirectory)`), an absolute one is used as it is. The recipe "New configuration key" names `appsettings.Development.json` for defaults, but a server without this key can't start in any environment | The default only in Development; a default in the options class | One visible home for the value; the key is not a secret | local |
| 11 | The first log message of the server, "Content {ContentVersion} loaded from {ContentFilePath}" (Information, event id 1000), uses a `[LoggerMessage]` source-generated method in `Api/Content/ContentLog.cs`, because the analyzers (CA1848, CA1873, errors in `src/`) reject `LogInformation` calls and arguments computed in the call | Suppress CA1848 | Structured templates as `14` and the server rules ask; no suppression needed | local |
| 12 | Startup tests use `factory.WithWebHostBuilder(host => host.UseSetting("Content:FilePath", …))`; the exception from `Program.cs` reaches the test from `factory.Services` unchanged | Environment variables; a custom factory class | One line per test; no shared state between tests | local |
| 13 | A JSON error always says where it is: System.Text.Json leaves the place out of some messages (an unknown field: "The JSON property 'maxWorker' could not be mapped …"), so the loader appends the exception's `Path`, `LineNumber` and `BytePositionInLine` in System.Text.Json's own format when the message has no `Path: `; the tests check that every JSON error names its place exactly once | Leave the message as it is; build an own message for every JSON error | Found while trying the how-to's example: a typo in a 200-line file needs its place; reusing the library's format keeps one style | local |
