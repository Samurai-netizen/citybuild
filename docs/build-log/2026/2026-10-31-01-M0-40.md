| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | `CommandSender` and its types live in `CityBuilder.Client.Net`; the pending list and outcome are plain classes the UI reads | put it in Core (it would need `ApiClient`, so Core would depend on Net: forbidden by `03`) | The sender needs `ApiClient` and `SnapshotMapper`, both in Net; views get it from `GameRoot` | local |
| 2 | "Max 3 attempts" is 3 requests in all: waits of 0.5 s and 1 s between them. The third value of the specified 0.5 / 1 / 2 is kept in the default policy but is never used | 3 retries (4 requests, so the 2 s is used) | The task says "max 3 attempts" and "success after two timeouts" fits both readings; the literal word wins. It is one number in `CommandPolicy.Default`. Owner: say if you meant 3 retries | local |
| 3 | Retried: network error, timeout, any 5xx (also a proxy's page, `CLIENT_INVALID_RESPONSE` with a 5xx status) and `CONCURRENCY_CONFLICT`. Not retried: every other 4xx, `RATE_LIMITED`, `AUTHENTICATION_REQUIRED`, and a 200 whose body is unusable | also retry `RATE_LIMITED` after `Retry-After` (`05` says it is retryable) | The task's list is explicit and says "never retry 4xx business errors". A rate limit's wait can be a whole window, and the player decides on it; a login problem is M0-41's. `05` line 191 says the same codes are *retryable*, which stays true: the sender just leaves that to the player | local |
| 4 | `CONCURRENCY_CONFLICT` waits the same backoff as the others instead of "at once" | retry it at once (`05` Idempotency) | One rule is simpler, and 0.5 s lets the lock holder finish. The id is the same, so it is safe either way | local |
| 5 | Waits go through an injected `Func<TimeSpan, CancellationToken, Task>` (default `Task.Delay`) and request ids through an injected `Func<Guid>` (default `Guid.NewGuid`) | `Task.Delay` and `Guid.NewGuid` directly; sleeping in tests | Tests must not wait real time and must know the ids. Same idea as the store's `Func<double>` clock (M0-39 decision 6) | local |
| 6 | A repeat of a pending non-stepper intent (same kind and arguments) returns the pending one's task instead of sending again | a second request id for every call | One intent has one request id: a double tap on Upgrade or a second tap on a tile is the same intent. Without it the second request would come back as `BUILDING_BUSY` or `TILE_OCCUPIED` and show an error for a command that worked | local |
| 7 | Worker targets: one lane per building. A new target replaces the waiting one (its task ends `Superseded`, no request); a target is sent after the 400 ms debounce and not before the building's earlier target has ended | send in parallel; one lane for all commands | Two parallel `assign-workers` for one building could reach the server in either order and leave the older target in force until the next poll. Different buildings and other commands stay independent | local |
| 8 | A failed or superseded intent is an outcome (`Failed`, `Superseded`) with the last `ApiError`; only a cancelled token throws | throw on failure | Same rule as `ApiClient`: a refusal is a result (`14` Correctness) | local |
| 9 | The sender removes an intent from `Pending` before its task completes | complete first | A caller that continues right after `await` must find the intent gone and the store already updated | local |
| 10 | A cancelled `CancellationTokenSource` is not disposed by the runner; the replacing call disposes a superseded one after `Cancel` returns | always dispose in the runner | Disposing a source from inside its own cancel callback blocked Unity's Mono (two tests hung). A cancelled source holds nothing but memory | local |
| 11 | `FakeTransport.TimeOut()` (a call that ends in the cancellation `ApiClient` turns into `CLIENT_TIMEOUT`) and a `FakeDelay` are test helpers; no existing test changed | wait the real 1 s timeout in tests | The timeout test would take seconds; `Timeout()` clashes with `System.Threading.Timeout` inside the class | local |

## Problems and surprises
- Two sender tests hung Unity's batch run for 10 minutes. Cause 1: a superseded target's runner ran inside `Cancel` and released the building's lane, so the next tap never found the waiting target (fixed: a replaced target touches nothing). Cause 2: disposing a `CancellationTokenSource` inside its own cancel callback (decision 10). A watchdog script (`run-filter.sh` in the scratchpad) found them one test at a time.
