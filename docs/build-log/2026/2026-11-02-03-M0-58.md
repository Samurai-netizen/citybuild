## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | New content is applied by rebuilding the content-bound parts through the start path (owner's choice A) | A live content holder read by ~25 classes; refetch and verify only, content used after a restart | Reuses the code that already builds everything from a `GameContent`; no class has to know about swapping | local |
| 2 | The API reports an incompatible client with a new error code `UNSUPPORTED_CLIENT_VERSION` (HTTP 426), which the server does not emit yet (owner's choice) | No new code: only the existing contract-mismatch case | The spec says the API "reports" it, and the later rejection task then has a code ready | project-wide (→ `12-decisions.md` row at finish) |
| 3 | The client version is logged as a log scope value (every line of the request), not as a line of its own; sanitised to 32 characters of `[A-Za-z0-9.+_-]`, else `invalid`; absent is `none`; nothing is refused | One new log event (id) per request; logging the raw header; rejecting now (spec: not now) | A scope gives every line the build without a new event and without extra volume; the raw header is client-controlled text (log forging) | local |
| 4 | The code is `UNSUPPORTED_CLIENT_VERSION`, not `CLIENT_VERSION_UNSUPPORTED` | The first name | `ClientErrorCodesTests` treats every `CLIENT_` code as client-only (the three failures before an answer exists), so a server code with that prefix would break its split | local (name of decision 2) |
| 5 | The guard test `EveryCode_HasASourceThatProducesIt` gets a `_reservedCodes` list for codes defined before anything produces them; a second test fails if a reserved code is already produced | A config key that makes the server refuse old builds (scope: spec says not now); a client-only code | Owner chose it (asked in session 1, G-Tests: loosening a test) | local |
| 6 | `ContentSync` is one class shared by the monitor and the sender, with events `ContentReplacing` (before the snapshot is applied) and `ContentReplaced` (after) | Refetch inside the monitor only; one event after applying | Commands also return snapshots (`05`: "the snapshot"), and the old parts must stop reading the store before a snapshot of other content reaches it, or `DisplayCity` would run new rules on old content | local |
| 7 | An incompatibility is `CLIENT_INVALID_RESPONSE` with status 200 from `ContentSync`, not a new state or code | A new `ApiError` code | `ConnectionMonitor.StateFor` already turns exactly that into `IncompatibleVersion`; the player-facing text exists | local |
| 8 | `ConnectionMonitor` and `CommandSender` take `ContentSync?` as an optional last argument; null keeps the old behaviour (other content incompatible) | A required argument (21 test call sites) | The game always passes it; the tests of the old rules stay as they were | local |
| 9 | `GameRoot` rebuilds by tearing down and building all content-bound parts (`TearDownContentParts` / `BuildContentParts`), not by patching them; open menus close | Patching each part's content in place | Each part takes its `GameContent` in its constructor (no setter); the rebuild reuses the start code, as the owner chose | local |
| 10 | `DisplayCity` gets `Dispose` (stops listening), the one change to a Core class | Letting the old one listen on | The old one would run old rules on the new content's snapshot inside the store's event | local |
