- **Plan:**
  1. **The words and flags as data.** `BuildingInspectorModel` (plain C#, `Presentation/Inspector/`): `Create(content, city, building, pending)` gives name, level, the status in words (`Waiting for Logs`, `Producing`, `Constructing`, `Upgrading to level 2`, `No workers assigned`, `Storage full: Planks`), the time to the next event (`ProgressDisplay.SecondsUntilNextEvent` through `DurationText`), the recipe card (`2 Logs → 1 Planks · 60/h at 3 workers`, rates from `ProductionDisplay.PerHour` at the current staffing), the stepper (`3 / 3`, − and + enabled or not with a reason, the pending target, the preview rate at the pending value) and the upgrade section (cost, time, `Max workers 3 → 6`, a disabled state with its reason in the server's check order). The pending stepper value and the pending upgrade come from `CommandSender.Pending`, so the model keeps no state of its own. EditMode tests: stepper limits, preview numbers, every status sentence, every disabled reason.
  2. **The screen.** `BuildingInspector` (a thin `UIDocument` component; layout `UI/Inspector.uxml` / `.uss`, a layout test for the names) writes the model into the elements, and raises `WorkersRequested(buildingId, target)` and `UpgradeRequested(buildingId)` on a press. A press over it is the UI's (`IsOverUi`, `UiRoot`).
  3. **The flow.** `InspectorFlow`: shows the inspector for the building on `TileSelection.Selected` while the placement flow is `Idle`, follows `DisplayCity.Changed` (once a second) and `CommandSender.PendingChanged`, closes when the building or the selection is gone; the stepper sends `CommandIntent.AssignWorkers(id, target ± 1)` (the sender coalesces and debounces), the upgrade button `CommandIntent.UpgradeBuilding(id)`; both are disabled while their intent is pending, so a double tap cannot double-submit. `GameRoot` creates it and extends `IsOverUi`. PlayMode tests: tap a building opens it, a tap on an empty tile closes it, − / + send the absolute target once, upgrade sends once, pending shows.

## Decisions
<!-- Every decision, when it is made, including small ones. Scope: local | project-wide (→ 12-decisions.md row) | architectural (→ ADR). -->
| # | Decision | Alternatives considered | Why | Scope |
|---|---|---|---|---|
| 1 | The task is built on top of the merged M0-50 (PR #70): the board row of M0-50 is set to `Done` in the start commit | Leaving it `In review` | The protocol says the next task sets the previous row to `Done` once the owner merged | local |
| 2 | The pending stepper value is read from `CommandSender.Pending` (the latest `AssignWorkers` intent of the building), not kept in the model | A local `pendingTarget` field in the inspector | One source of truth: the sender already coalesces a target and shows it as pending until it ends; a closed and reopened inspector shows the same value | local |
| 3 | The model takes an `InspectorPending` value, not the sender's list; `InspectorPending.From(buildingId, pending)` does the reading | `Create(..., IReadOnlyList<PendingCommand>)` | `PendingCommand` has an `internal` constructor, so an EditMode test cannot make one; the value keeps the model testable with plain numbers, and `From` is covered in PlayMode with a real sender (step 3) | local |
| 4 | Item and rate words moved into a shared `ItemText` (`Presentation/Ui`), and `BuildCardModel` uses it | A second private copy in the inspector | Two private copies of `Quantities` / `ItemName` would be real duplication (`02` rule 13); the build card tests cover the move | local |
| 5 | Status words: `Under construction`, `Upgrading to level N`, `Producing`, `Ready` (idle and able to run, and a cottage), `No workers assigned`, `Waiting for <item>`, `<Item> storage is full`; time: `Ready in`, `Upgrade done in`, `Next batch in` | Showing the engine's `StallKind` names | Words for the player; the reason itself is the engine's `StallReason`, not a second rule | local |
| 6 | The stepper stays on an upgrading building and hides only while it is built (and for a cottage) | Hiding it during an upgrade | The server accepts `AssignWorkers` on an upgrading building (only `Constructing` is `BuildingBusy`) | local |
| 7 | The plus button is off when the target plus one needs more free workers than the city has, counting the target already on its way against them | Comparing with the free workers alone | A pending increase has not reached the city yet, so the free count alone would allow two taps that the server refuses (`WORKER_LIMIT` / not enough workers) | local |
| 8 | The upgrade section is always shown; at the highest level it says `Highest level reached` with no price | Hiding it | The player sees why there is nothing to press; the task asks for a disabled state with a reason | local |
| 9 | The panel sits at the right under the HUD (top margin 124 in panel units, width 440) with sort order 0.8: over the HUD (0.5), under the build menu (1), the placement bar (2) and the toasts (3) | Bottom right (the placement bar's place) | The bar is hidden whenever the inspector is open (the flow shows one or the other), but a sheet of the build menu is wide and should cover the inspector, not the reverse | local |
| 10 | A press on − or + sends the target one step away from the value the screen shows (which is the pending target when one is on its way), so rapid taps accumulate in the sender's coalescing instead of in the inspector | Counting taps in the inspector | One source of truth (decision 2); the sender already waits out the 400 ms pause and keeps only the newest target | local |
| 11 | The inspector stays closed while the placement flow is not `Idle`, and reopens by itself when the flow ends if the tile is still selected | Clearing the selection when a card is picked | `PlacementFlow` already clears the selection when it starts and ends; the inspector only listens to `PlacementFlowModel.Changed` and adds no rule of its own | local |
