## Sessions

### Session 1 — 2026-11-16 · Claude Code
- **Plan** ([PLAN] task: waits for the owner's approval before step 1):
  1. **Domain and port.** `PlayerEvent` (player, type, detail, outcome, city clock, time) and the event type names in
     `CityBuilder.Domain/Metrics/`; `IPlayerEventRepository.Add` in Application. Unit tests of the record's checks.
  2. **Table.** `PlayerEventRow`, its configuration, the repository, migration `AddPlayerEvents`: `player_events` with
     `ix_player_events_player_id_created_at` and `ix_player_events_event_type_detail`, FK to `players` `ON DELETE CASCADE`. Tests on
     PostgreSQL: mapping round-trip, the migration from empty and from `AddBuildingPaused`, the cascade, the pinned column list (no
     name, address or body column). Regenerate `db-schema.md`.
  3. **Recording in the city's transaction.** `CityTransaction.Record(event)` stages events; they are written with the city's save, and
     when the work saved nothing, by the runner just before its commit (so a refused command at an unchanged instant still gets its
     row, and `state_version` stays). A rollback drops them. Tests with fakes and on PostgreSQL.
  4. **Command events.** `CommandPipeline` records `command.<type>` with `accepted` or the rule's error code. `ICityCommand` gets
     `EventDetail(CityState)` (the building type, the research id, the item; `null` for the road and courier commands). A replay, an
     idempotency conflict, a shape refusal and a concurrency conflict record nothing. A test over every `ICityCommand` type.
  5. **Settlement events.** From the closed `Settlement`: `research.completed` (the research id) and `building.completed`
     (`<type>:<level>`), once each, also inside a long offline settlement. Both for `GET /city` and for commands.
  6. **Player and session events.** `player.created` and the first `session.start` in the first login's transaction;
     `session.start` when a settling request comes later than the session gap after the last seen second.
  7. **Guards.** Architecture test: only the recorder path writes `player_events`, and nothing in Application or the engine reads
     them. Golden, determinism and performance tests unchanged. The API contract test set unchanged (no client-visible difference).
  8. **Docs** per the Docs impact table, the plan board (CR-0009 rows, 88 → 90 tasks), `10` and `30` scope lines, CHANGELOG.
