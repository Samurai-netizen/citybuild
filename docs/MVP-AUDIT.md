# M0 final MVP audit

The audit of the full chain of one player action, from a tap in Unity to what the screen shows after the server's answer (M0-83, 2026-11-17).
For each link: where its truth lives, how it can fail and what then happens, and the tests that hold it. Then the Definition of Done of
`docs/plan/M0-PLAN.md` §1, box by box, with its evidence. No feature was added for this audit; the gaps it found are follow-ups (end of page).

Test classes are under `server/tests/` (server and engine) and `client/CityBuilder/Assets/_Project/Tests/` (Unity, `EditMode` or
`PlayMode`). The rule-by-rule view (every invariant, error code and threat with its tests) is `docs/testing/COVERAGE-MATRIX.md`; this page
follows one request instead.

## The chain

```mermaid
flowchart LR
  A[Input] --> B[Intent] --> C[DTO] --> D[HTTP] --> E[Auth] --> F[Validation] --> G[City lock]
  G --> H[Receipt] --> I[Settle] --> J[Rules] --> K[Zero-length advance] --> L[Persistence + ledger]
  L --> M[Snapshot] --> N[Client store] --> O[Prediction] --> P[UI]
```

## Gaps found (follow-ups, none blocks M0)
- **Expired token on a command** (M0-C-4, P2): `CommandSender` does not log in again on a 401, so the first command after expiry is refused once.
- **`COURIER_BUSY` on assign-workers** has no HTTP test; the engine test and the error mapping cover it (M0-D decision 1).
- **Empty database at start** (M0-C-2, P3): EF logs history-table error lines before the first migration; harmless.
- **Application identifiers** are the Unity template's (`docs/BUILD.md`); a store build needs real ones.
- **Not verified here:** the Windows and iOS builds, and the APK on a phone (owner, `docs/BUILD.md`).

The M1 backlog that takes these up is in `docs/HANDOFF-M0.md` (M0-84).
